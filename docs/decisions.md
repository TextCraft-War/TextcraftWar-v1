## D1 · 四 crate 分层，依赖方向由编译器强制

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`domain` / `protocol` / `storage` / `server` 四个 crate，单向依赖。
  `domain` 的 `[dependencies]` 保持为空。
- **理由**：多 crate 的价值不是"模块化"，是**让编译器守住依赖方向**。
  规则层若没有 sqlx 这个依赖，"有人在 domain 里写 SQL"就编译不过，不靠自觉。
  同时 `storage` 需要把数据库行翻译成 domain 类型，所以 domain 必须独立成 crate，
  否则 `storage → server` 会形成环。
- **被否**：单 crate（`pub(crate)` 管不住"谁调用了 sqlx"）；
  v2 的七上下文 DDD 切分（那是 22k 行规模下的答案，对 v1 是过度切分）。

## D2 · 数据库用 sqlx 直写 SQL，不用 ORM

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`sqlx 0.8`，默认用 `query_as`（运行期校验），不用 `query!`（构建期校验）。
- **理由**：
  1. 本项目的查询形态是"少数表 + 条件 UPDATE + 批量 UPDATE"，ORM 的关系图能力用不上。
  2. 既然 `storage` 本来就要把行翻译成 domain 类型，ORM"实体即模型"的最大优势已经消失。
  3. `query!` 需要编译时连活库，会让没装 PG 的机器和 CI 直接失败，代价大于收益。
- **被否**：sea-orm（仍需一层映射，且中文标识符要 `#[allow]` 绕 derive 问题）、diesel（要 `diesel_cli`，更重）。
- **注**：防 SQL 注入靠的是参数绑定（`.bind()`），不是 ORM；两者等价。

## D4 · v1 只有中文，玩家可见文本收敛到 `文案` 模块

## D5 · lint 分级：只有"会变成线上事故"的规则才 deny

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`clippy::all` deny；`pedantic`/`nursery` warn；函数 200 行、认知复杂度 25、参数 10；
  测试内放开 `unwrap`/`expect`/`panic`。
  保留 deny 的：`unsafe_code`、`panic`/`unwrap_used`/`expect_used`/`todo`/`unimplemented`、
  三类数值转换、`await_holding_lock`、`print_stdout`/`print_stderr`/`dbg_macro`。
- **理由**：原配置（三组全 deny、80 行函数、全 pub 项强制文档、warnings 视为 error）是金融系统标准，
  对一个 2 人规模的文游属于自缚手脚。而 `unwrap` 在游戏服务器里一次失败就是整个连接挂掉，这条值得保留。
- **注**：`bacon` 的 clippy 作业去掉了 `-D warnings`，否则 pedantic 的 warn 会被重新提升为 error。

## D6 · v1 没有地理系统，地区 = 频道组

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：地区没有坐标、地形、距离、邻接。所有地区在空间上是同一个点。

## D7 · 三个独立的兵力池，各挂一张表

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：

  | 池 | 表 | 语义 |
  |---|---|---|
  | 私人军队 | `玩家` | 玩家自己操作兵器的兵员，**整数** |
  | 联军军队 | `联军` | 联军共享兵员，也是驻军的唯一来源 |
  | 驻军 | `地区` | 从联军军队转化而来，守地区 |

- **理由**：三者语义不同（个人操作员 / 组织共享 / 驻防单位），生命周期也不同。
- **衍生结论**（非原始设计，是推出来的）：
  - 联军军队同时是"防掠夺的最后一层壳"和"驻军的来源"，**屯兵与派兵是互斥取舍**。
  - 炮击的反击可以**跨实体**：重炮在玩家库存里，操作它的联军军队在联军账上。
    因此加入大联军等于给自己名下的重炮配了备用炮手。
- **被否**：驻军 = "把私军搬过去"（会让三个池子退化成两个）。

## D8 · 战争是整数消耗战，不做建制与单位

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：没有部队编成、没有单位类型、没有战斗模拟。兵力是整数，武器是库存。
  空袭打联军军队（攻方零损耗），炮击打私人军队（守方可能反击一次），掠夺在对方军队归零后进行。
- **理由**：原版就是这么设计的，且它天然满足"战争结算不能卡"的性能红线——
  每个阶段都是两个整数相减，纯函数算完再一条条件 UPDATE。
- **被否**：《新马列文游策划》里的组织度 / 战场宽度 / 增援 / 陆战空战模拟（那是另一个游戏，属 v3）。

## D9 · 地区 UID 是随机 6 位数字，同时充当访问凭证

- **日期**：2026-10-29 ｜ **状态**：已确定（成本门槛待定）
- **决定**：地区 UID 为 `100000`–`999999` 的随机数。**不知道 UID 就打不到这个地区。**
- **理由**：作者的设计。它在"没有地图"的前提下制造了一个信息层：
  物资放地区比放身上安全，前提是 UID 没泄露。
- **已知风险**：100 万个组合可枚举，"保密"靠的是成本而不是数学。
  缓解方向：攻击地区消耗军事行动点，且**失败不退款**（待定）。
- **连带义务**：UID 不得出现在任何公开可见处——别人的查询结果、错误提示、日志、战报文案。

## D15 · 库存统一成一张表，用「所有者」区分归属

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`库存(所有者类型, 所有者_id, 物品, 数量)` 一张表管所有物品。
  所有者可以是玩家（背包）、联军（仓库）、地区（地区仓库）。
  实体表上不再有任何资源列或装备列。
- **理由**：
  1. "地区仓库能存大部分东西"意味着背包和仓库是同一个机制，只是所有者不同。
     分成两张表后，"掠夺"就变成"从 A 表搬到 B 表"，以后加物品要改三处。
  2. 统一后掠夺只有一个函数：改两行库存。
  3. 物品是 `TEXT`，加一种物品不需要迁移。
- **代价**：读一个玩家的资源多一次查询或 join。2 人规模可忽略。
- **被否**：`玩家` 表加资源列 + 独立的 `玩家装备`/`地区仓库` 表（三套机制做同一件事）。

## D16 · 装备是枚举

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`装备` 是 Rust 枚举，落库为 `TEXT`（`equipment:<name>`）。
  不做"id + 定义表"的数据驱动方案。
- **理由**：v1 只有 6 种装备，枚举能在编译期穷尽检查（`match` 漏一个就编译不过）。
  真到几十种装备、需要策划配表时再改，届时 `TEXT` 列不需要迁移。

## D17 · 建筑挂地区，用 0–100 完成度，不做建筑定义总表

- **日期**：2026-10-29 ｜ **状态**：已确定（清单与数值待定）
- **决定**：v1 有建筑。建筑挂在**地区**下，一种建筑一个地区一份，
  进度是 **0–100 的完成度**，到阈值才解锁效果。
  表只有 `地区建筑(地区_id, 建筑, 完成度)`，**没有**全局建筑定义总表。
- **理由**：
  1. 建筑是**地区的属性**，跟着地区易主。这样"控制地区"才有收益，
     和"物资放地区仓库更安全"是同一条激励——地区是据点，不是一个仓库编号。
  2. 原版就是完成度制（学校 60% 解锁城市招募工人、炼钢厂 70% 解锁炼钢）。
     阈值让"建到能用"成为明确的目标节点，比"升到 3 级"更好理解。
  3. 不建定义总表：清单只有几种，且效果要参与规则计算，写在 `domain` 里能 `match` 穷尽
     （同 D16）。真到几十种再数据驱动，`建筑` 列是 `TEXT`，不需要迁移。
- **被否**：等级制（`0..N` 每级加成，和原版手感不同）；
  《新马列文游策划》的建筑位 / 劳动力分配 / 电力模型（v3 候选）。

## D18 · 库存按所有者整体读写；联军仓库 v1 不放装备

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：
  1. `查库存(所有者类型, 所有者_id)` 一次返回该所有者的**全部物品**，规则算完再写回变化的行。
  2. 三种所有者（玩家 / 联军 / 地区）**同时成立**：玩家背包、联军仓库、地区仓库都能存东西，
     机制完全相同，区别只在"谁能访问"。
  3. 装备**不进联军仓库**：v1 不提供"把装备存进联军仓库"的指令。
- **理由**：一次掠夺要同时搬多种物品，单物品零散查会变成 N 次往返，
  中途失败还会留下"搬了一半"的状态；整读整写让一次战争收敛成"一个事务里的几行 UPDATE"。
  装备按 D8 挂在玩家名下（谁造谁有），联军的共享体现在 `联军军队`，不在共享装备。
- **被否**：单物品一次一查（往返多、难做原子性）；
  "联军成员共用装备"（会让"谁造的装备谁开火"这条边界消失，炮击反击的跨实体设计就没法算了）。

## D19 · 基础类型用 PostgreSQL DOMAIN

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：`非负计数`（`BIGINT NOT NULL DEFAULT 0 CHECK (VALUE >= 0)`）、
  `时间戳`（`BIGINT NOT NULL`）、`百分比`（`INT NOT NULL DEFAULT 0 CHECK (VALUE BETWEEN 0 AND 100)`）、
  `地区uid`（`INT NOT NULL CHECK (VALUE BETWEEN 100000 AND 999999)`）四个 DOMAIN 定义在
  `01_domains.sql`，表定义里只写语义名（`驻军 非负计数`）。
  `稳定度` 不用 `非负计数`——它可以为负。
- **理由**：
  1. 同一条约束原来要在七八个列上各写一遍 `BIGINT NOT NULL DEFAULT 0 CHECK (… >= 0)`，
     加一个计数字段就得再抄一次，迟早漏写。
  2. 表定义从"约束堆"变回"说明书"：一眼看到 `驻军 非负计数` 比看到一长串类型修饰好读。
  3. 改约束用 `ALTER DOMAIN … ADD CONSTRAINT`，一次性覆盖所有用到它的列。
  4. DOMAIN 不是 `enum` 类型：加一个"用哪种基础类型"的列不需要 `ALTER TYPE`，也不改变列的可比性。
- **已验证**：sqlx 0.8.6 对 DOMAIN 列的读写完全正常。PostgreSQL 在结果集描述里报的是
  **底层类型**（`SELECT 数量 FROM 域测试` 的 `\gdesc` 是 `bigint`，含 `SELECT *`），
  所以 `query_as::<_, (i64,)>` 直接解得出来，不需要 `::bigint` 之类的 cast。
- **被否**：每列各写一遍 CHECK（重复且容易漏）；PG `enum` 类型（加变体要 `ALTER TYPE`，
  且和"枚举存 TEXT"的约定冲突）；建 `字段定义表` 做数据驱动（规则要参与计算，必须能 `match`）。

> 后来又加了第 5 个 `可空时间戳`（`BIGINT`，NULL = 还没发生过），用于 `出生保护至`
> 和各种 `上次…时间`，见 D28。

## D20 · 中文标识符不写双引号

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：迁移与查询里的中文表名、列名一律不加双引号：`SELECT 名称 FROM 联军`。
- **理由**：PostgreSQL 只把 **ASCII 大写字母**折叠成小写，非 ASCII 字节原样保留。
  中文没有大小写，所以加不加引号是同一个标识符——已实测：不加引号建表、加引号查、反过来查，全部通过。
  代价是满屏 `"` 的视觉噪音和"漏一个引号就报错"的心智负担，而在中文标识符上收益为零。
- **边界**：含空格、ASCII 大写字母、保留字的标识符才必须加引号；本项目不用这类名字。
- **推翻**：D10 里"中文列名在 SQL 里必须双引号"那一条（当时的判断有误）。

## D21 · 迁移一表一文件，语义写进数据库目录

- **日期**：2026-10-29 ｜ **状态**：已确定
- **决定**：
  1. 初始建表按表拆成多个迁移文件（`01_domains.sql` … `41_channel_binding.sql`），
     不把七张表塞进一个文件；以后每张表的演进沿自己的序号往后加。
  2. 字段语义用 `COMMENT ON TABLE/COLUMN` 写进数据库目录，不写成字段列表中间的 `-- 注释`。
- **理由**：
  1. 一表一文件让"这张表怎么长出来的"能单独读完；一个大文件里夹着七张表，改一个字段要滚半天。
  2. `COMMENT ON` 是数据库元数据：`\d+ 玩家` 直接可见，pg_dump 会带走，ORM/客户端也能读到。
     塞在列中间的 `--` 只对打开这个文件的人有效，而且打断字段列表的阅读。
  3. 不凑列对齐：中英混排的显示宽度不可靠，加一个长字段就得重敲整张表的空格。
- **被否**：一个大迁移文件里按表加章节注释；字段中间夹 `--` 说明。

## D22 · 迁移文件名：两位版本号 + 英文短语

- **日期**：2026-10-30 ｜ **状态**：已确定
- **决定**：
  ```text
  01_domains.sql          10_coalition.sql      11_player.sql
  20_region.sql           21_region_building.sql
  30_inventory.sql        40_platform_binding.sql   41_channel_binding.sql
  ```
  1. 文件名格式 `<两位版本号>_<英文短语>.sql`；**只有文件名是英文**，SQL 内容与数据库标识符照旧是中文。
  2. 版本号必须 **≥ 1**（sqlx 约定文件名前缀是"大于零的整数"）。
  3. 版本号按 **10 分段预留空位**：1x 联军/玩家、2x 地区、3x 库存、4x 绑定。
- **理由**：
  1. 文件名会出现在 `_sqlx_migrations.description`、日志、命令行补全里。ASCII 在这些地方最省心
     ——本次验证时中文日志在 `Start-Job` 管道里就已经是乱码了。中文文件名 sqlx 读得了
     （`0001_基础类型.sql` 实测可用），但没有任何好处，只有编码风险。
  2. 分段预留 = 往中间插新表不用重编号。重编号就是改**已应用迁移的版本号**，
     等价于让所有已有数据库重建。
  3. 版本号 0 属于契约外：`00_domains.sql` 在 sqlx 0.8.6 上实测能跑（ledger 里 version = 0），
     但文档写的是"大于零"，将来某版把它当非法文件**静默忽略**时，
     表现是"线上少一个 DOMAIN"而不是编译错误。不值得为省一个数字冒这个险。
- **代价**：`01` 单独占一段，看着不如 `00` 整齐；换来的是不违反 sqlx 契约，
  且 `crates/storage/src/pool.rs` 的测试能直接断言"版本号 ≥ 1 且严格递增"。
- **被否**：`0001_基础类型.sql` 这类中文文件名（D21 初版，本地无碍但无收益）；
  `00_` 开头的零号版本（契约外）。

> 这次重命名发生在**还没有任何已部署数据库**的时候。若某个本地库已经跑过旧编号（1–8），
> `_sqlx_migrations` 里留着旧版本号，启动会报 `VersionMissing`——删库重跑即可，
> v1 未上线，不为此提供数据迁移脚本。

## D23 · 跨平台身份：绑定表 + 显式注册，绑定不是合并

- **日期**：2026-10-30 ｜ **状态**：已确定
- **背景**：读了 v2（`TextcraftWar-v2`）的做法——身份是 `玩家配置表` 上的
  `onebot` / `discord` / `telegram` 三列，绑定走"出码 → 对方输码 → 主人最终同意"三步。
- **决定**：
  1. `平台绑定(玩家_id, 平台, 平台_uid)` **行存**，一个玩家 1..N 个平台账号。
     两条唯一约束：`UNIQUE (平台, 平台_uid)`（对外：账号只属于一个玩家）、
     `UNIQUE (玩家_id, 平台)`（对内：一个玩家在同一平台只有一个账号）。
  2. **注册显式**：`注册` 建玩家 + 写第一条绑定；未注册时其他指令回 `not_registered`。
  3. **绑定只能挂"还没有玩家"的平台账号**；已经是一个玩家的账号拒绝绑给别人。
  4. 三步口令：`绑定账户`（出 6 位码，5 分钟）→ `确认绑定 <码>`（在另一个平台）→
     `最终同意`（回原平台，**先显示对方的平台/uid/昵称**）。
     每个玩家同时只保留一个待确认口令；口令在 `server` 内存里，失败 3 次作废。
  5. v1 不做解绑。
- **理由**：
  1. v2 把"平台"编码进了 schema：加一个平台要改两张表、`支持平台` 联合类型、i18n 文案键
     和若干展示指令（实际散在 8 处代码里），且平台名被当动态列名用。
     行存之后，加平台只是多一个字符串值，零 DDL——和"枚举存 TEXT"同一条思路。
  2. v2 的唯一性只在应用层查一次（平台列上没有唯一索引），并发或手改库都能让
     同一个平台账号指向两个玩家，`get` 返回哪行不确定。行存把这条交给数据库。
  3. v2 在**同一个平台**绑第二个账号会直接 `set` 覆盖第一个：旧账号从此解析不到玩家，
     而且不报错。`UNIQUE (玩家_id, 平台)` 从结构上堵死。
  4. 显式注册是绑定的前提：自动注册会把每个平台账号都变成玩家，
     "这个账号还没注册"这个状态被吃光，绑定永远无法发起。
  5. **不合并**就省掉了整个"资源归属"难题：两个号各有 500 工人时怎么算？
     v2 用一条检查绕开（目标账号已有玩家就拒绝），这是它最值得抄的一条。
- **代价**：玩家多一步 `注册`；未注册的人发指令会先被打回一次。
- **被否**：v2 的"每平台一列"（加平台改结构）；"把两个已有账号合并成一个"
  （资源归属无解，且等于给刷号开口子）；口令入库（v1 单实例，收益是"跨实例"，
  成本是过期清理与并发确认）。
- **遗留**：v2 的口令靠 `setTimeout` 过期，进程被杀会漏一条；v1 不依赖定时器，
  每次校验时比对 `过期时间`，所以重启只是让口令提前消失，不会留下永远有效的口令。

## D26 · 玩家不留名称，寻址靠平台账号（@）

- **日期**：2026-10-30 ｜ **状态**：已确定
- **决定**：
  1. `玩家` 表**不加 `名称` 列**，也不做重名检查/改名工单。
  2. 需要"指向某个玩家"的指令（`邀请`、`炮击`、`掠夺`）一律写成 `@玩家`。
  3. 协议 `command` 增加 `mentions`：`[{ "platform": "…", "userId": "…" }]`，由 Koishi
     把各平台的 @ 语法解析成 id 后传入；**Rust 不解析 @ 文本**。
- **理由**：
  1. v2 为"玩家名"单开了一套命名上下文（`名称是否审核` + 改名工单 + 审核群推送）。

  3. @ 的文本格式每个平台都不一样（`<at id="…"/>`、`<@123>`、`@昵称`）。
     在 Rust 里解析等于把三套平台怪癖搬进游戏服务器；Koishi 本来就已经解析好了。

  1. **物资不进列**：v2 有二十多个资源列，加一种资源就要 `ALTER TABLE`；我们用 `库存`（D18），
     加物品只改 catalog + 枚举。
  2. **布尔改成时间戳**：`今日是否签到`/`小时是否生产` 这种每日/每小时重置的布尔，

  把 `曾加入联军列表` 存成 json（真要做"联军履历"就开表，json 列没法查、没法建索引）。

## D29 · 自增 BIGINT 主键 + 只给地区一个秘密 uid

> **[部分废止]** 「玩家不需要 uid」被 D30 推翻（跨群寻址需要 `P…` 编号）；保留的部分——uid 不是主键、
> 不带前缀落库、不从自增 id 推导——已由 [arch/data-model.md](./arch/data-model.md) 承接。原文折叠存档：

<details>
<summary>展开 D29 原文</summary>

- **日期**：2026-10-30 ｜ **状态**：已确定
- **背景**：v2 的玩家和地区都是"自增 `id` + 混淆 `uid`"两个标识，自增 id 图的是查询性能。
- **决定**：
  1. **所有实体的主键都是自增 `BIGINT`**（`玩家` / `联军` / `地区` / 两张绑定表），
     所有关联列也是 `BIGINT`（`联军_id`、`地区_id`、`玩家_id`、`库存.所有者_id`）。
     `库存` 和 `地区建筑` 用自然复合主键，不额外加代理键。
  2. **只有 `地区` 有对外 uid**：6 位随机数字，`INT`，`UNIQUE`。`玩家`、`联军` 都没有。
- **理由**：
  1. 自增 `BIGINT` 主键：8 字节定长、比较不经过 collation、索引条目小、插入顺序友好
     （少页分裂）。`TEXT` 主键要按排序规则比较，还带 varlena 头。2 人规模下其实无感，
     但这是**免费**的——没有理由先写错、以后再改。
  2. 地区需要 uid，是因为它是**访问凭证**而不是编号：不知道就打不到（design 2.2）。
     凭证要能**轮换**，所以它绝不能是主键——换一次 uid 只需改一行，
     当主键就得改所有引用行（data-model 4.3 已写）。
  3. 玩家**不需要**任何编号：身份是平台账号，指令里用 `@`（D26）。
     给玩家一个 uid 反而制造歧义——它到底是"秘密"还是"编号"？
     打玩家本来就不需要凭证，所以玩家不该有凭证式编号。
  4. v2 的 uid 是 sqids 编码（**可逆的混淆**），目的是遮住自增序列，让玩家看不出
     "我是第 37 个注册的"；我们的地区 uid 是**随机数**，不可从 id 推导，
     因为它是真秘密。两种东西目的不同，不要混为一谈。
- **被否**：
  - 拿 uid 当主键（换凭证 = 改所有引用行）。
  - 给玩家加 uid（没有寻址需求，还会被误当成秘密）。
  - UUID 主键（16 字节、随机分布导致索引页分裂；我们要的"不可枚举"是地区的
    访问控制问题，不该用主键选型去解决）。
- **遗留**：将来若真要给玩家一个对外编号（排行榜/战报展示），加一个**可空 + `UNIQUE`** 的
  `uid`，只用于展示，**绝不参与关联**。现在不加，因为还没有任何东西要显示它。

> **D30 推翻了"玩家不加 uid"这一条**：跨群寻址确实需要编号（`P123456`）。
> 保留的部分是：uid 不是主键、不带前缀入库、不从自增 id 推导。

</details>

## D30 · 玩家与地区都有 6 位秘密编号（P / R 前缀）

- **日期**：2026-10-30 ｜ **状态**：已确定 ｜ **部分推翻**：D29 的"玩家不需要 uid"
- **决定**：
  1. `玩家.uid` 与 `地区.uid` 都是**随机 6 位数字**（`100000`–`999999`），`UNIQUE`，
     落库是 `INT`（DOMAIN `六位编号`），**前缀不进库**。
  2. 显示与输入都带前缀：玩家 `P123456`，地区 `R123456`。命令解析靠前缀区分
     "找玩家"还是"找地区"。
  3. 两套编号都是**秘密凭证**：别人的编号不得出现在公开输出里，自己的可以在 `我的资料` 里看。
  4. `P` 与 `R` 是两个独立命名空间，数字可以重复。
- **理由**：
  1. **跨群寻址是真的需求**：`@某人` 只在同一个群有效；要打另一个群的人、
     或者跨平台找同一个人，必须有一个可以传递的编号。
  2. 前缀让解析无歧义，也允许两种编号共用同一个数字空间——不用为玩家和地区
     设计两套不同的位数。
  3. **随机而非派生**：从自增 id 推出来的编号会暴露"我是第 37 个注册的"，
     而且特别方便枚举，那就不是凭证了（v2 的 sqids 就是这个性质：可逆混淆，不是秘密）。
  4. 不落前缀：表本身就知道自己是玩家还是地区，多存一个字母只是让索引变大、比较变慢。
- **代价**：注册/建地区时要随机生成 + 撞了重试（90 万个号，2 人规模撞不到）；
  `uid` 多一条唯一索引。
- **被否**：
  - 不加玩家编号（@ 只在本群有效，跨群打不到人）。
  - 拿自增 id 当编号（可枚举、泄露注册顺序）。
  - 把前缀存进库（冗余、索引变大、比较变慢）。
  - 用 UUID 当编号（32 字符，玩家没法在群里口述）。

## D32 · 生产次数与招募清零走全服定时结算，进度存在单行表

- **日期**：2026-10-30 ｜ **状态**：已确定 ｜ **取代**：D31 里"每个玩家存结算锚点"的做法
- **决定**：
  1. `玩家` 表**不存** `生产次数结算时间`、**不存** `上次招募时间`。
  2. 两个批处理：每小时 `生产次数 = LEAST(8, 生产次数 + 1)`；每天 0 点 `今日招募数量 = 0`。
  3. 全服进度存在单行表 `系统状态(id = 1, 上次生产结算, 上次日结)` 里；
     启动时与每次 tick 都按时间差补算，漏掉的整小时数一次性补上。
- **理由**：
  1. 这是全服同一时刻的动作，不是每个玩家各自的时间线——按人存锚点属于把批处理写成逐个计算，
     一条 SQL 能解决的事变成 N 条。
  2. 但"纯 cron"有个真实的坑：进程在结算点没跑（部署、崩溃、机器重启）就漏一次。
     漏一次生产次数还好，漏一次日结就是**全服一整天不能招募**。
     存两个全服时间戳，启动时 `UPDATE 玩家 SET 生产次数 = LEAST(8, 生产次数 + 漏掉小时数)`
     就补回来了，代价只是一行数据。
  3. 单行表比"给每个玩家加两个锚点"便宜得多：2 个时间戳 vs 2 × 玩家数 个时间戳。
- **代价**：读玩家状态时如果要判断"现在能生产几次"，得知道上次结算时间——
  所以 `系统状态` 和 `玩家` 必须一起读（一次查询或一次 join）。
- **被否**：纯 cron 不存进度（漏跑就永久少结算，且无法补）；
  每个玩家各存锚点（D31 的初版，列多、更新也要逐行）。

- **日期**：2026-10-30 ｜ **状态**：已确定 ｜ **修正**：D34 里"宣称人口/兵力是派生值、不落列"

## D39 · 实际人口是「成员总人口之和」，不是「工人之和」

- **日期**：2026-10-30 ｜ **状态**：已确定 ｜ **修正**：D38 第 2 条

- **理由**：宣称的是**人口**，对外喊的是国力。只数工人会把兵员藏起来——

- **代价**：对内查询多 SUM 三列；口径再变只改一条 SQL——派生值不落列的好处在这里兑现

- **被否**：保持 `SUM(成员.工人)`（D38 的原口径，作者明确否掉）。

## D40 · 每条指令恰好一个事务；事务的机制在 storage，边界在 server

- **日期**：2026-10-30 ｜ **状态**：已确定 ｜ **修正**：storage 设计文档 §2.1
  「本 crate 里不出现 `begin()`」的旧约定
- **决定**：
  1. `storage` 导出 `事务`（对 `sqlx::Transaction` 的类型别名）与
     `开事务` / `提交` / `回滚` 三个动作；查询函数签名收 `&mut PgConnection`，
     调用方在事务里写 `&mut *事务`。
  2. `server` **不依赖 `sqlx`**：事务句柄对它是**不透明**的，想在那层写一条 SQL
     会直接编译失败。
  3. 每条指令（**含纯读**）恰好一个事务：成功 `提交`，失败 `回滚`。
- **理由**：
  1. 只有**一条**事务路径，就没有「读走池、写走事务」的分叉，
     也没有「某个读指令以后要写，签名全改」的返工。
  2. 错误上下文（`操作` 名）统一在 storage 加好，server 拿到的失败已经带位置。
  3. 「只有 storage 懂数据库」从纪律变成编译期事实——这正是当初分四个 crate 要买的东西。
  4. 签名用 `&mut PgConnection` 而不是泛型 `impl Executor`：`Executor` 也接受 `&PgPool`，
     一次调用就可能绕过事务直接打在池上；收连接堵死这条道，还省掉一套泛型。
- **代价**：只读指令多一对 BEGIN/COMMIT（微秒级）；事务里依旧不许 await 外部 IO
  （本来就不许，这条没变）。
- **被否**：server 直接依赖 sqlx 自己 `begin()`（依赖栅栏破一个口子，
  早晚有人在这层写 SQL）；读指令不开事务（两条路径迟早漂移）。

## D41 · 注册 = 建玩家 + 首条绑定，出生地区 = 注册所在频道所属地区

- **日期**：2026-10-30 ｜ **状态**：已确定
- **决定**：
  1. `注册` 在一个事务里按固定顺序完成：
     **串行化**（D42）→ 幂等查绑定（已注册就回编号）→ 查频道地区 → 建玩家 → 写绑定。
  2. 频道必须已绑地区，否则回 `no_region`，**不建玩家**。
  3. `玩家.驻扎地区_id` = 该地区；其余列取默认值（初始工人/资源为 0，
     等 design 第六节待定 1 的数值定稿后再补「新手礼包」）；
     `出生保护至` 暂不写（等 design 待定 6 定时长）。
  4. 编号在 `server` 生成：随机 6 位（`100000..=999999`），撞号重试 8 次；
     `storage::插入玩家` 用 `ON CONFLICT (uid) DO NOTHING RETURNING id`，
     返回 `None` = 撞号——存储层只回答「这个号被占了吗」。
  5. 注册回执显示自己的 `P…` 编号——这是玩家拿到凭证的唯一入口，群里可见。
- **理由**：频道 = 地区是 v1 的空间模型（D6），注册信息里唯一稳定的「你在哪」
  就是所在频道；让玩家出生在 `NULL` 地区，后续所有需要位置的东西都无从谈起
  （v1 没有 `迁移` 指令）。生成策略属于服务器：塞进存储层就没法在测试里构造撞号，
  重试次数也成了拍脑袋的魔法数。
- **代价**：新部署必须先有地区 + 频道绑定才能注册（v1 没有建地区指令，靠 SQL 播种）。
- **被否**：玩家出生在 `NULL` 地区；storage 内部生成编号并重试；
  注册时直接写一份新手礼包（数值未定，写 0 又要改）。

## D42 · 同一平台账号的注册串行化（事务级 advisory lock）

- **日期**：2026-10-30 ｜ **状态**：已确定
- **决定**：注册事务开头执行
  `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`，键是 `平台:账号` 字符串。
- **理由**：注册是「查了再写」：两个并发的 `注册` 都查不到绑定，就各建一个玩家，
  只有一个能拿到 `UNIQUE (平台, 平台_uid)` 的绑定，另一个要么留一条
  **没有绑定的孤儿玩家**、要么回系统错误。advisory lock 让第二个请求等第一个提交后
  再查绑定，直接回「已经注册过」。锁随事务结束自动释放：不需要解锁流程，
  连接被回收也不会漏锁。
- **代价**：每次注册多一次 SQL 往返；锁必须和注册在**同一个事务**里，拿错了就是安慰剂
  ——所以 `插入绑定` 故意不带 `ON CONFLICT` 兜底：真撞上唯一约束说明锁没生效，
  让它以数据库错误炸出来，比静默吞掉好。
- **被否**：`ON CONFLICT DO NOTHING` + 出错让玩家重发（孤儿玩家留在库里）；
  表锁 / 行锁（要锁的是「这个账号正在注册」这个谓词——表锁殃及全服，
  行锁锁不到**还不存在的行**，advisory lock 正好补这个空档）。

## D45 · 连接池与事务用 Newtype 封装——"不透明句柄"变成物理事实

- **日期**：2026-10-31 ｜ **状态**：已确定 ｜ **修正**：D40 第 1 条的实现方式（类型别名 → newtype）

## D46 · 读写分流：纯读不开事务，写函数只收 `&mut 事务`

- **日期**：2026-10-31 ｜ **状态**：已确定 ｜ **修正**：D40 第 3 条「每条指令（含纯读）恰好一个事务」
- **决定**：
  1. `storage` 导出 `enum 执行者<'a> { 池(&'a 连接池), 事务(&'a mut 事务) }`。
  2. **读**查询收 `执行者`：纯读传 `执行者::池`（借连接 → 查 → 还，**不开事务**）；
     事务内的读（注册的"锁住 → 再查绑定"，D42）传 `执行者::事务`。
  3. **写**函数不收 `执行者`，只收 `&mut 事务`——拿池直接写库编译不过。
- **理由**：
  1. D40 的"一条事务路径"代价被低估了：连接池上限 8，聊天机器人的流量是
     **高频纯读夹杂低频写**。每条读指令在事务生命周期内独占一个连接
     （BEGIN…COMMIT 期间），群里稍微热闹就触发池排队——读多写少的场景下，
     给读挂事务是拿最贵的资源干最便宜的事。
  2. 类型系统分流：读指令将来要写库，处理函数改收 `&mut 事务` 即可，
     调用点编译器逐个指出来；而"写绕过事务"在签名层面就不成立。
  3. advisory lock 的正确性不受伤：注册事务里的读走 `执行者::事务`，
     与锁同一条连接，串行化语义与 D42 完全一致。
- **代价**：读与写两套签名形状（读 `执行者`、写 `&mut 事务`）；
  分发层从"统一开事务"变成按指令选择路径。
- **被否**：维持纯读也开事务（D40 原案，见理由 1）；读也收 `&mut 事务`
  强制全事务（同上）；泛型 `impl Executor`（D40 已否——它连裸池都收）。

     它是 `protocol.md` 的镜像，三张表（码 / 文案 / 级别）对每一层穷尽 `match`。
  2. **连接拆两层**：`ws.rs`（模块 `连接`）只管帧——读、写、Ping/Pong、关闭；
     `session.rs`（模块 `会话`）管握手状态机（5s/token/版本）与每条指令的门卫
     （512 字符、平台编码合法、平台与握手一致）。270 行的 `connection.rs` 一拆为二。
  3. **解析产出 `domain::指令`**（D44 的兑现）：`command.rs` → `parser.rs`（模块 `解析`），
     路由 `match` 领域枚举而非字符串；认不出的原文不是领域概念，
     留在 `解析::结果::不认识`，由分发层结合身份决定错误码。
  4. **业务流程归 `handlers/`**（模块 `处理器`）：每类指令一个文件，
     统一形状"事务句柄 + 来信 + 注入的时间 → 玩家文案"。
  5. **时间注入**：处理器不取"现在"，`时间` 参数由分发层注入
     （`时钟::现在()` 只在分发层调用一次）——"跨天签到"这类测试不用动系统时钟。
  6. **调度器骨架**（模块 `调度`）：tokio 后台任务，60 秒一个 tick
     （`MissedTickBehavior::Skip`），每轮纯读 `系统状态`（不开事务，D46）；
     main.rs 在迁移之后拉起，与监听并行。补算本体随 S4 进来，
     串行化点（`锁定状态` 的 `FOR UPDATE`）已在 storage 就位。
- **理由**：审计指出的三个结构性问题一次修掉——(a) 平坦错误枚举里"谁该断连、
  谁该 `error` 级"全靠人记，分层后判断写在层上；(b) `connection.rs` 把帧搬运、
  握手状态机与门卫揉在一起，270 行三种职责；(c) 解析器私有的 `指令` 枚举让
  "服务器认识的动作"与领域词表两处漂移。时间注入与调度器是 S4（经济闭环）的
  前置：前者是可测性，后者是补算的挂载点。
- **代价**：错误从一层变三层，构造点要写 `.into()`；`domain::错误` 的
  `物资不足` / `数量溢出` 还没有指令路径产生，码与文案先落到占位
  （穷尽 match 是提醒，S3 落地时随 `protocol.md` 一起定稿）。
- **被否**：给 `domain::错误` 实现 `错误码()`（码是协议词汇，且 E0117）；
  每个错误码一个 Rust 枚举（散成两份必漂移，D43 已否）；调度器现在就实现补算
  （S4 的活，骨架只挂心跳与兜底日志）。

## D49 · 面向 200+ 指令的演进规范：语法分治、管线门禁与触发线

- **日期**：2026-10-31 ｜ **状态**：已确定 ｜ **背景**：外部顾问"微内核 + 垂直切片"方案
  经逐条审计后采纳主体、修正六处（任务书存
  [docs/顾问提示词-200指令架构.md](./顾问提示词-200指令架构.md)）。
  v1 路线图约 30 条指令，本条按**长期演进到 200+ 条**定规范；全部按触发线**增量**落地，
  不做 big-bang（刚完成 D44–D48，重排违背路线图自己的"竖切不横切"）。
- **决定**：
  1. **语法分治**：名词膨胀（物品/建筑/兵种）由 `domain` 词表枚举吸收——加第 33 种物品
     时解析器、分发、handler、SQL 全部零改动；指令变体的增长只允许来自**动词句式**。
     带参指令自 S4 起用零分配 `词元游标` 解析（位置参数 + 断言结束）；
     **多余参数默认拒绝**（映射 `bad_request`），`注册` 豁免（维持现状——Koishi 侧可能带尾巴）；
     未知词头仍是 `unknown_command`，未注册优先（身份先行不变）。
  2. **身份前置**：分发管线在路由前统一做身份拦截，分支直接收 `绑定`——
     30 条指令**想漏都漏不掉**（随本条之后的第一个提交落地）。
  3. **错误码政策**：6 个协议码不变。规则拒绝（物资不足、冷却中、需驻地而无驻地）
     → `bad_request`，联军权限不足 → `forbidden`（随 S7 首条联军指令一起定稿，
     顺带清掉 D48 的占位码）；**`no_region` 保留 D41 原义"注册频道未绑地区"**，
     不挪用为"无驻地"。解析错误归业务层——D48 三层壳与三张穷尽表一字不动。
  4. **文案类型门禁**：handler 成功返回值改为 crate 内**不透明新类型 `玩家文本`**
     （字段私有，仅协议封包处拆包）——业务代码拼玩家字符串直接编译失败，
     §十"文案唯一出口"从纪律变成类型。
     **`千分位` 保持 `i64` 签名**：稳定度可以为负，顾问方案的 u64 版会丢负号。
  5. **准入声明 + 凭据**：每条指令的身份/冷却要求以穷尽 `match` 的 `准入要求`
     声明在 domain（"权限属于 domain"的兑现；零 IO——读库与加锁在 server/storage，
     核验产出**私有构造凭据**作为规则函数必填参数，防漏检与并发重入）。
     随首条冷却类指令（`签到`）引入身份声明，随 S6/S7 引入凭据。
  6. **并发守卫（S6 触发）**："同类双实体"锁（对轰两块区域）用
     `有序双标识` + 类型状态事务在编译期强制升序；**跨类全序**（玩家→地区→联军→库存）
     与 3+ 实体仍走组合存储函数 + 并发集成测试（storage impl.md 2.7）——
     不宣称"死锁已编译期消灭"。
  7. **测试漏斗**：规则全进 domain 纯函数单测（词表矩阵遍历）；
     解析穷尽表测、文案千分位金样测试零 IO；真库集成只测事务、锁与并发，
     按 SQL 模板级写，不按指令级写（否则 200 条指令 = 600 个慢测试）。
- **触发线**（全文见 roadmap「指令规模化触发线」，到线才动）：
  指令变体 > 25 → 两级域枚举；`text.rs`/`parser.rs` > 500 行 → 转目录按域分文件
  （parser 不许成为下一个千行文件）；指令 > 40 → `指令词头` 唯一事实源 + 帮助/近似匹配；
  首个跨实体写指令前 → 并发守卫；`model.rs` > 1000 行 → 按域拆文件。
- **理由**：
  1. S3 实测：加一条指令的**架构税**只有 7 行（parser +2、dispatch +5），
     其余是任何架构都要写的本体代码——顾问第一版的"8 个文件"把两者混算了。
     真正会痛的是 200 条时的 `text.rs`（约 700 行）、帮助永不漏写、多人不抢 `dispatch.rs`；
     触发线让这些痛点出现**之前**有据可依，**之前不**预付重构成本。
  2. 四类最易错的规范（文案外泄、乱序加锁、漏写权限/冷却、漏配帮助/错误映射）
     全部转化为编译期检查（不透明类型、移动语义、穷尽 match）。
  3. `#[path]` 中文模块摩擦（E0754）决定了文件粒度上限：按 7 大业务域粗分
     （每文件 15~25 条指令），全仓转接控制在 20 处以内。
- **代价**：单条指令架构税从 7 行涨到约 11~15 行、分散 4~5 处编译器强制点
  （换顶层 `dispatch.rs` 零冲突与帮助强制）；`玩家文本`/`有序双标识`/凭据
  三个类型守卫的概念成本。
- **被否**：`业务拒绝(String)` 与 UI Builder 撒文案（违 §十与 i18n 预留、废 D48
  穷尽同步、改协议契约——顾问已撤回）；运行时 trait 注册表（丢穷尽保护 +
  热路径 `Box<dyn Future>` 装箱）；一指令一文件（`#[path]` 爆炸）；
  domain 存量数值字段全量新类型化（成本未入账，只对新增解析参数用 `非零数量`
  类强类型）；"kernel 冻结"表述（词头映射必变，冻结的只是顶层主干）。
