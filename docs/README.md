# 文档

> 状态：施工中 ｜ 最后更新：2026-10-29

这套文档只有一个目标：**让三个月后的你（或另一个 AI agent）能在一小时内接手这个项目**。

## 怎么读

按这个顺序，每一步都不依赖后面的内容：

1. [design.md](./design.md) — 这是个什么游戏，规则是什么
2. [architecture.md](./architecture.md) — 代码为什么这样分层
3. [data-model.md](./data-model.md) — 表结构与领域类型（唯一事实来源）
4. [protocol.md](./protocol.md) — 服务器和 Koishi 怎么说话
5. [roadmap.md](./roadmap.md) — 现在做到哪了，下一步做什么
6. [decisions.md](./decisions.md) — 每个重要决定背后的理由

各 crate 的 `docs/design.md` 是实现约定，**读代码前看**。

---

## 职责边界（本文档体系最重要的规则）

**一份事实只写在一个地方。** 别处只放链接，不复制。

| 文档 | 只写这些 | 绝不写 |
|---|---|---|
| `design.md` | 玩法、规则、数值、指令 | 表结构、代码结构 |
| `data-model.md` | 表结构、领域类型、不变量 | 玩法规则、SQL 查询 |
| `architecture.md` | crate 分层、依赖方向、数据流 | 玩法规则 |
| `protocol.md` | wire 格式、字段、错误码 | 内部类型、玩法 |
| `roadmap.md` | 切片、验收标准、状态 | 设计细节 |
| `decisions.md` | 决策与理由 | 当前实现细节 |
| `crates/*/docs/design.md` | 本 crate 的实现约定 | 全局规则 |

出现矛盾时的优先级：**代码 > `design.md` > 其他文档**。代码和文档不一致，说明文档该改了，或者代码写错了——但一定是其中一件事，不允许"都行"。

## 状态标记

每份文档头部必须写状态和日期：

| 标记 | 含义 |
|---|---|
| `施工中` | 正在写，内容可能整段变 |
| `草案` | 结构已定，细节待填 |
| `已落地` | 与代码一致，可以直接信 |

现在的项目整体处于 **施工中**：四个 crate 都还是空骨架，架构已定、玩法已对齐、代码未开始。

## 更新纪律

1. **改了行为，同一次提交里改对应文档。** 文档和代码分两次提交，视为没做完。
2. **新增决定 → 在 `decisions.md` 追加一条，不改历史条目。** 要推翻旧决定，新写一条并注明「取代 D-x」。
3. **数值改动只改 `design.md`。** 别处引用时只写"见 design.md"，不抄数字。
4. **不要写"将来会……"。** 要么写进 `roadmap.md`，要么就别写。
