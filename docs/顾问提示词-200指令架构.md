# 任务：为 TextcraftWar 设计"200+ 指令仍健康"的长期架构方案

你是一名 Rust 架构顾问。这个项目已经有一套严格纪律和刚完成的架构重构（D44–D48），
你的上一版建议有一半方向对、一半与项目硬规范冲突，且部分论据过时（如"27 种物品"，
实际词表 32 项）。这次的规则：**先读代码再下结论，所有论断给可核查的证据，不确定就明说。**

## 0. 背景事实（先承认这些，再思考）

- 项目：文字战争游戏服务器，纯后端，WebSocket + PostgreSQL，中文标识符代码库。
  AGENTS.md 是最高规范；docs/decisions.md 决策**只追加**；路线图 S4–S8 待做，
  v1 约 30 条指令，但业主要求按**长期演进到 200+ 指令**设计（赛季内容、运营指令、
  更多物品/建筑带来的参数化变体）。
- 当前结构：四 crate 单向依赖 `server → {domain, storage, protocol}`、`storage → domain`，
  由 Cargo 依赖图强制。`domain` 零 IO、零 async、零外部依赖；`storage` 只写 SQL + 行翻译
  （server 的依赖树里没有 sqlx，编译期事实，D45/D47）；`server` 管解析、事务编排、文案。
- 刚完成的 S3 实测数据（新增一条**零参纯读**指令"我的资料"的全账单）：
  - 架构归因的税：`parser.rs` +2 行、`dispatch.rs` +5 行、`error.rs` +0 行（复用既有错误）；
  - 任何架构都必写的本体代码：`command.rs` +3 行、handler +20 行、文案 +40 行、
    storage 读函数 +50 行、集成测试 3 个用例。
  - **"身份先行"已收敛**：`dispatch.rs` 的 `查身份` helper（约 54 行处），每个非注册分支
    一行调用。
- 当前文件规模：dispatch 80 行 / parser 120 / error 303（三张穷尽表全在这一个文件里）/
  text 234 / domain model.rs 736 / handlers/account.rs 165。
- protocol.md 错误码现 6 个：`bad_request` / `unknown_command` / `not_registered` /
  `no_region` / `forbidden` / `internal`。
- **非显然的硬约束**：rustc 拒绝非 ASCII 文件名（E0754），所有中文模块名靠
  `#[path = "英文文件名.rs"]` 转接；子模块的 `#[path]` 相对所在目录解析。
  **文件粒度越细，转接 shim 越多**——模块拆分方案必须把这个摩擦算进成本。

## 1. 你上一版方案被否的部分（要么接受，要么逐条反驳）

1. "加指令要改 7~8 个文件/跨 3 crate"——把**本体代码**（规则函数、SQL、编排、文案、测试，
   任何架构都要写，你自己的 Step 表也要碰 3 个 crate）算进了架构税。真实税 ≈ parser 2 行 +
   dispatch 5 行 + 有新失败时 error.rs 一个文件里的几行。footprint 断言必须区分这两类。
2. `业务拒绝(String)`（错误携带排版好的文本）被否，理由：
   (a) 违反 AGENTS.md §十"玩家可见文本统一走 文案 模块"与 §七的 i18n 预留——
   builder 方案照样把"木材"这类字面量撒进各 feature 文件；
   (b) 废掉 D48 三张表（错误码/玩家文案/日志级别）的**编译器穷尽 match 强制同步**；
   (c) 改 protocol.md 对外契约。想翻案必须先回答这三条。
3. "`指令` 移出 domain"被否（D44）：纯查指令也给 domain 加 1 行变体，代价可忽略；
   换来解析器产出领域类型、分发按语义路由。
4. "kernel 冻结"论证有洞：新指令的**词头属于哪个 feature** 的映射总要有人记——
   要么 kernel 路由表跟着改（没冻结），要么各 feature 轮流试解析（顺序与歧义是坑）。
   你的新方案必须精确回答词头映射住哪、加指令时它变不变。
5. 目标形状（按业务域对齐、纵切）本身没被否——被否的是**现在就 big-bang 重构**和
   违反硬规范的实现手段。

## 2. 硬约束（方案违反任何一条即无效）

- AGENTS.md 全部条款。尤其：crate 边界与依赖方向；storage 之外禁碰数据库；
  玩家可见文本统一收敛 `文案` 模块（§十是禁令不是品味）；数值一律千分位；
  错误必须 `Result` 显式传播、thiserror；禁 panic/unwrap/println；
  clippy `all` deny + pedantic/nursery warn；性能红线=战争结算低延迟、禁全表锁；
  仅 crates.io 依赖（cargo deny 把关）。
- docs/decisions.md 只追加。想改任何决策（含 AGENTS.md 本身），显式写
  "建议修改第 X 条/DXX"，给理由、迁移路径与代价——**不许隐式绕开规范**。
- v1 单实例、无缓存、i18n 只有中文但接口要留给将来的多语言实现替换。
- 迁移必须增量：每步一个提交、全部测试绿、不阻塞 S4–S8 玩法交付。不接受 big-bang。

## 3. 200+ 指令时真正要解的问题（上一版没碰的才是重点）

1. **指令语法空间分析**：先把 200+ 条拆成指令族（查询/经济写/军备/战争/联军管理/运营…）。
   "生产 <物品> <数量>"一条指令覆盖 32 种物品——真正的增长是**指令族**还是**解析目标**？
   这个分析决定一切后续设计。不许跳过直接谈文件布局。
2. **参数解析工具**：带参指令（`招募工人 50`、`宣战 R123`、`生产 钢铁 100`）的切分、
   枚举解析、数量上限、多余参数策略；解析失败算什么（bad_request？unknown_command？
   领域错误？）；工具在哪一层、怎么复用、怎么测。
3. **指令发现**：200 条时玩家必需要 `帮助`、分域帮助、近似匹配提示（"你是想找 X 吗"）。
   元数据（名称/参数/简介/所属域）的数据源在哪？与路由表是否同一份事实？
4. **权限与冷却的声明方式**：联军权限 1–3 级+职务、签到日限、炮击冷却。AGENTS.md 说
   "权限属于 domain"，但强制需要读库——零 IO 的 domain 怎么强制？声明在哪、检查在哪、
   怎么保证 200 条指令没人漏写？
5. **错误码政策**：6 个码在 200 指令时够不够？"规则拒绝"统一一个码+带内玩家文案，
   还是每类拒绝一个码？给决策 + 对 Koishi 哑管道与 i18n 的影响分析。
6. **文案组织**：§十"唯一出口"在纵切下怎么活？给具体形态（如 `文案/` 变成目录、按域分
   文件），并说明千分位与排版约定如何仍被强制。
7. **domain 内部组织**：model.rs 736 行，按域拆（player/economy/region/coalition/war）？
   拆的粒度怎么和 #[path] 中文模块摩擦权衡？实体与"按域的规则函数"怎么归置？
8. **测试策略**：200 指令 × 每条集成测试（真库）是什么形状？哪些该下沉为 domain 纯函数
   单测、文案金样测试？真库集成测试只留给谁（事务编排/锁行为）？
9. **分发机制选型**：flat enum（现状）vs 两级域枚举 vs 静态元数据表+enum vs trait 对象
   注册表。各自的真实代价（穷尽 match 的编译器保护、async/借用、每条消息的开销——
   路由热路径不许有可观分配）。给 200 指令下的推荐与理由。
10. **并发与锁**：跨实体写指令（战争/联军划拨）加锁顺序按主键升序（storage impl.md 2.7）。
    你的方案里新 handler 怎么保证不破坏这条？编译器能不能帮上忙？

## 4. 产出格式（九节，缺一不可）

1. **现状核实笔记**：你读了什么、实测了什么数字（行数/文件数），纠正了你上一版的哪些错。
2. **指令语法空间分析**：指令族分类表 + 每族的语法形态与参数类型。
3. **目标架构**：目录树 + 每模块职责一句话 + 哪些不变量由**编译器**强制（指明机制：
   穷尽 match/类型私有/可见性），哪些只靠约定（并说明为何可接受）。
4. **四个关键机制设计**：参数解析工具、指令元数据（帮助/权限/冷却）、错误码政策、
   文案组织。各给核心签名（Rust 伪码，中文标识符，遵守项目命名规范）。
5. **三张足迹表**：零参纯读 / 带参写 / 跨实体写（战争类）三种代表指令，
   在你的方案下的精确文件清单与行数量级，**并排对照现状**，只对差值负责。
6. **分阶段迁移路线**：每阶段=一组提交，全部测试绿，与 S4–S8 对齐；每阶段写**触发条件**
   （出现什么信号才做），并写明"什么坚决不做"。
7. **被否选项**：你考虑过并放弃的方案连同理由；对本文件第 1 节各条要么接受要么逐条反驳。
8. **自我批判**：现行设计哪里比你的方案好？你的方案让什么变差了？承认得越具体越可信。
9. **D49 草稿**：可直接追加进 docs/decisions.md 的条目（沿用现有条目格式：决策、
   理由、被否的替代）。
