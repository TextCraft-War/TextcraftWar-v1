# 数据模型

> 状态：**草案，待作者确认** ｜ 最后更新：2026-10-29
>
> 本文是**表结构与领域类型的唯一事实来源**。`storage`/`domain` 的文档只写实现细节，不再重复定义。
> 玩法规则见 [design.md](./design.md)。

## 一、建模约束

这五条适用于所有表，后面不再逐条重复：

1. 表名、列名用中文；SQL 里必须加双引号（`"玩家"`）。
2. 所有时间列是 `BIGINT`，存 **Unix 秒**。不用 `TIMESTAMP`——跨时区、跨平台，整数最省事。
3. **不建物理外键。** 全部是逻辑引用，一致性由应用层的事务保证。
   原因：联军会解散、地区会易主，物理外键的级联语义在这里全是错的。
4. 枚举列一律存 `TEXT`（英文小写），读出后在 `storage` 里 `TryFrom` 成领域枚举。
5. 一表一实体，不搞宽表；热字段与冷字段分开。

## 二、关系

```
玩家 ──┬──< 平台绑定        (一个玩家可绑多个平台账号)
       ├──< 玩家装备        (装备库存)
       └──> 联军            (可空：新玩家没有联军)

联军 ──< 地区               (控制方，可空：无主地区)

地区 ──< 地区频道绑定        (一个地区可绑多个频道，跨平台)
```

## 三、表定义

### 3.1 `玩家`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键，不对外暴露 |
| `工人` | `BIGINT` | `NOT NULL DEFAULT 0` | 从事生产的人口 |
| `私军` | `BIGINT` | `NOT NULL DEFAULT 0` | **操作兵器的兵员**，与工人争抢同一批人口 |
| `生活资料` | `BIGINT` | `NOT NULL DEFAULT 0` | 主资源，也是工资的来源 |
| `世界货币` | `BIGINT` | `NOT NULL DEFAULT 0` | 由生活资料兑换而来 |
| `科技` | `BIGINT` | `NOT NULL DEFAULT 0` | 解锁军备的门槛 |
| `稳定度` | `BIGINT` | `NOT NULL DEFAULT 50` | **可以为负**；负值不能生产 |
| `工资` | `BIGINT` | `NOT NULL DEFAULT 0` | 高于基准提升稳定度 |
| `联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id` |
| `联军职务` | `TEXT` | `NOT NULL DEFAULT 'member'` | `member` / `officer` / `leader` |
| `出生保护至` | `BIGINT` | `NULL` | Unix 秒；`NULL` = 已过保护 |
| `创建时间` | `BIGINT` | `NOT NULL` | |

索引：`玩家 (联军_id)`。

### 3.2 `联军`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `名称` | `TEXT` | `NOT NULL UNIQUE` | |
| `联军军队` | `BIGINT` | `NOT NULL DEFAULT 0` | 共享兵员，**驻军的唯一来源** |
| `生活资料` | `BIGINT` | `NOT NULL DEFAULT 0` | 联军仓库 |
| `创建时间` | `BIGINT` | `NOT NULL` | |

### 3.3 `地区`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键 |
| `uid` | `INT` | `NOT NULL UNIQUE` | **对外访问凭证**，6 位数字，保密 |
| `名称` | `TEXT` | `NOT NULL` | |
| `控制方_联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id`；`NULL` = 无主 |
| `驻军` | `BIGINT` | `NOT NULL DEFAULT 0` | 从联军军队转化而来 |
| `生活资料` | `BIGINT` | `NOT NULL DEFAULT 0` | 地区仓库 |
| `世界货币` | `BIGINT` | `NOT NULL DEFAULT 0` | 地区仓库 |
| `创建时间` | `BIGINT` | `NOT NULL` | |

索引：`地区 (控制方_联军_id)`。

> **为什么 `uid` 不是主键**：主键是对内的、要参与 join 和索引；`uid` 是对外的秘密。
> 两者混用会让"改一次凭证 = 改一遍所有关联行"，且自增主键对 B 树更友好。

### 3.4 `平台绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `玩家_id` | `BIGINT` | `NOT NULL` | |
| `平台` | `TEXT` | `NOT NULL` | `onebot` / `discord` / `telegram` |
| `平台_uid` | `TEXT` | `NOT NULL` | 平台侧用户 id |
| `绑定时间` | `BIGINT` | `NOT NULL` | |

约束：`UNIQUE (平台, 平台_uid)` —— 一个平台账号只能绑一个玩家。
索引：`平台绑定 (玩家_id)`。

### 3.5 `地区频道绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `地区_id` | `BIGINT` | `NOT NULL` | |
| `平台` | `TEXT` | `NOT NULL` | |
| `频道_id` | `TEXT` | `NOT NULL` | 群 / 频道 id |
| `绑定时间` | `BIGINT` | `NOT NULL` | |

约束：`UNIQUE (平台, 频道_id)` —— 一个频道只能属于一个地区。
反向**不唯一**：一个地区可以绑多个频道（这正是跨平台共享的实现方式）。

### 3.6 `玩家装备`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `玩家_id` | `BIGINT` | `NOT NULL` | |
| `装备` | `TEXT` | `NOT NULL` | 枚举名，与领域枚举对齐 |
| `数量` | `BIGINT` | `NOT NULL DEFAULT 0` | |

主键：`(玩家_id, 装备)`。

> 装备独立成表，而不是在 `玩家` 上加 N 个列：加一种装备不应该等于 `ALTER TABLE`。

## 四、领域类型（`domain`）

### 4.1 标识与时间用 newtype

```rust
/// 玩家主键。
pub struct 玩家Id(pub i64);

/// 联军主键。
pub struct 联军Id(pub i64);

/// 地区主键（内部 id，不是对外的 uid）。
pub struct 地区Id(pub i64);

/// Unix 秒。
pub struct 时间(pub i64);
```

理由：四个参数全是 `i64` 的函数，早晚会把 `玩家Id` 和 `联军Id` 传反，而且编译器不会吭声。

### 4.2 实体

```rust
/// 玩家。
pub struct 玩家 {
    pub id: 玩家Id,
    pub 工人: i64,
    pub 私军: i64,
    pub 生活资料: i64,
    pub 世界货币: i64,
    pub 科技: i64,
    pub 稳定度: i64,
    pub 工资: i64,
    pub 联军: Option<联军Id>,
    pub 联军职务: 联军职务,
    pub 出生保护至: Option<时间>,
}

/// 联军。
pub struct 联军 {
    pub id: 联军Id,
    pub 名称: String,
    pub 联军军队: i64,
    pub 生活资料: i64,
}

/// 地区。
pub struct 地区 {
    pub id: 地区Id,
    /// 对外访问凭证：6 位数字，不得出现在任何公开输出里。
    pub uid: u32,
    pub 名称: String,
    pub 控制方: Option<联军Id>,
    pub 驻军: i64,
    pub 生活资料: i64,
    pub 世界货币: i64,
}

/// 装备库存。键是装备种类，值是数量。
pub struct 装备库存(pub std::collections::BTreeMap<装备, i64>);
```

### 4.3 枚举

```rust
/// 接入的聊天平台。
pub enum 平台 { Onebot, Discord, Telegram }

/// 联军内的职务。v1 只用它判断"能不能驻军"。
pub enum 联军职务 { 成员, 干部, 元首 }

/// 战争器械。v1 只有这些。
pub enum 装备 {
    战斗机,     // 巡逻防空
    轰炸机,     // 空袭
    运输机,     // 掠夺
    重炮,       // 炮击
    防空弹药,   // 消耗品，拦截空袭
    地对空导弹, // 部署在地区
}
```

> 指令与事件的枚举由 [design.md 第五节](./design.md) 的指令表派生，不在这里重复列举，
> 避免加一条指令要改两处。

### 4.4 跨实体聚合：`战场快照`

战争一次要读**三张表**（攻方玩家、守方玩家、守方联军）外加可能的一张地区表。
domain 不查库，所以 `server` 负责把这些读出来拼成一个值传进去：

```rust
/// 一次战争结算所需的全部输入。
pub struct 战场快照 {
    pub 攻方: 玩家,
    pub 攻方装备: 装备库存,
    pub 守方: 玩家,
    pub 守方装备: 装备库存,
    pub 守方联军: Option<联军>,
    pub 现在: 时间,
}
```

攻陷地区另有一个更小的快照（攻方装备 + 地区 + 攻方联军）。

## 五、不变量

这些是**任何操作都必须维持**的性质。domain 的每个函数在返回前都应该保证它们成立：

| 不变量 | 说明 |
|---|---|
| `工人 + 私军 = 总人口` | 扩军是"工人 → 私军"，不是凭空造人；私军阵亡 = 人口永久损失 |
| `工人 >= 0`、`私军 >= 0` | |
| `联军军队 >= 0`、`驻军 >= 0` | 驻军从联军军队转化，不能凭空出现 |
| `玩家.联军` 为 `None` ⇒ `联军职务` 无意义 | 建议默认 `成员`，读取时忽略 |
| `地区.uid` ∈ `[100000, 999999]` 且唯一 | |
| `地区.控制方` 为 `None` ⇒ 无主 | ❓ 无主地区能否有驻军，待定 |

## 六、存储映射（`storage`）

- 行类型 `玩家行` / `联军行` / `地区行`：`#[derive(sqlx::FromRow)]`，字段与列一一对应，
  **只在 `storage` 内部可见**，绝不带 `Serialize`。
- 领域类型：`domain::玩家` 等，**绝不带 `FromRow`**。
- 两者之间用 `TryFrom<玩家行> for 玩家` 转换，转换失败 = 数据损坏，返回内部错误。
- 装备：`玩家装备` 的多行聚合成 `装备库存`，在 `storage` 里做完。

## 七、待确认

1. **`工人 + 私军` 是否严格恒定？** 扩军消耗多少工人换 1 私军（1:1？），裁军退回多少（原版跑掉 1/4）。
2. **地区仓库用列还是通用物品表？** 现在用 `生活资料`/`世界货币` 两列；如果以后要存装备，就得改成通用表。
3. **装备是枚举还是数据驱动？** 现在是枚举（编译期穷尽检查）。装备多了以后可能要改成"id + 定义表"。
4. **`联军职务` v1 需要几级？** 现在三级，只用于"能不能驻军"。
5. **无主地区能不能有驻军？** 直接影响 `控制方` 和 `驻军` 的一致性约束。
