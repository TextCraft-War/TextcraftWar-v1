> 状态：**草案（表结构已定，玩法数值待填）** ｜ 最后更新：2026-10-30
>
> 本文是**表结构与领域类型的唯一事实来源**。`storage`/`domain` 的文档只写实现细节，不再重复定义。
> 玩法规则见 [design.md](./design.md)。

## 一、建模约束

这五条适用于所有表，后面不再逐条重复：

1. 表名、列名用中文，**不写双引号**。PostgreSQL 只折叠 ASCII 大写字母，中文标识符原样保留：
   `SELECT 名称 FROM 联军` 与 `SELECT "名称" FROM "联军"` 等价。
   只有含空格 / ASCII 大写 / 保留字的标识符才需要引号——本项目不用这种名字（D20）。
2. 计数列用 DOMAIN `非负计数`，时间列用 `时间戳`（`BIGINT` + Unix 秒），不要逐列写
   `NOT NULL DEFAULT 0 CHECK (… >= 0)`。不用 `TIMESTAMP`：跨时区、跨平台，整数最省事。见 4.0。
3. **不建物理外键。** 全部是逻辑引用，一致性由应用层的事务保证。
   原因：联军会解散、地区会易主，物理外键的级联语义在这里全是错的。
4. 枚举列一律存 `TEXT`（英文小写），读出后在 `storage` 里 `TryFrom` 成领域枚举。
5. 一表一实体，不搞宽表。

## 二、关系

```
玩家 ──┬──< 平台绑定         (1..N 个平台账号，每个平台最多一个)
       ├──< 库存             (所有者 = 玩家)
       └──> 联军             (可空：新玩家没有联军；职务/贡献/加入时间在玩家行上)

联军 ──┬──< 地区             (控制方，可空：无主地区)
       ├──> 地区             (首都，可空；必须是本联军控制的地区)
       ├──< 库存             (所有者 = 联军，即"联军仓库")
       ├──< 联军分配记录     (把仓库里的东西分给成员)
       └──< 联军资本增量     (每天一行：成员利润合计)

地区 ──┬──< 地区频道绑定     (一个地区可绑多个频道，跨平台)
       ├──< 库存             (所有者 = 地区，即"地区仓库")
       └──< 地区建筑         (建筑挂地区下)
```

## 三、库存：一张表管所有物品

**这是本文档最重要的一个决定。**

玩家的背包、联军的仓库、地区的仓库，是**同一个机制**：某处存着若干种物品各多少个。
所以只用一张 `库存` 表，用 `所有者类型 + 所有者_id` 区分归属。

```sql
库存(所有者类型 TEXT, 所有者_id BIGINT, 物品 TEXT, 数量 非负计数)
主键 (所有者类型, 所有者_id, 物品)
```

好处：

- **掠夺就是"改两行库存"**，不管是从玩家搬还是从地区仓库搬，代码是同一个函数。
- 加一种物品不用改任何表结构。
- "地区仓库比身上安全"这条玩法，就是"同一张表里，地区那一行的 uid 更难拿到"。

代价：读一个玩家的资源要多一次查询（或一次 join）。2 人规模下可以忽略。

### 3.1 物品枚举

```rust
/// 库存里能放的东西。
pub enum 物品 {
    资源(资源),
    装备(装备),
    弹药(弹药),
}
```

具体有哪几种、落库编码是什么，见 **[catalog.md 第二节](./catalog.md#二物品)**——那是唯一真相。
这里只固定结构：**物品 = 资源 | 装备 | 弹药**；装备比资源多一个"每件所需兵员"（出击闸门），
弹药是一次性消耗品。

`库存.物品` 列不加 CHECK 约束：加一种物品只改代码，不改表（理由见 catalog 第一节）。

### 3.2 三类所有者的语义

| 所有者 | 落库值 | 含义 | 谁可以访问 |
|---|---|---|---|
| 玩家 | `player` | 随身物资，**最不安全**（打玩家不需要 UID） | 本人 |
| 联军 | `coalition` | 联军仓库 | 联军成员（v1 仅元首） |
| 地区 | `region` | 地区仓库，**最安全**（需要地区 UID 才能打） | 有权限的联军成员 |

## 四、表定义

### 4.0 基础类型（DOMAIN）

重复的 `BIGINT NOT NULL DEFAULT 0 CHECK (VALUE >= 0)` 收进 PostgreSQL 的 DOMAIN，
表定义里只写语义名字：

| DOMAIN | 底层类型 | 约束 | 用在哪 |
|---|---|---|---|
| `非负计数` | `BIGINT` | `NOT NULL DEFAULT 0 CHECK (VALUE >= 0)` | 工人、私军、科技、工资、联军军队、驻军、库存数量 |
| `时间戳` | `BIGINT` | `NOT NULL` | 所有 `创建时间` / `绑定时间`（Unix 秒） |
| `可空时间戳` | `BIGINT` | 可空 | `出生保护至` 与各种 `上次…时间`（NULL = 从没发生过） |
| `百分比` | `INT` | `NOT NULL DEFAULT 0 CHECK (VALUE BETWEEN 0 AND 100)` | 地区建筑的 `完成度`、联军的 `税率` |
| `六位编号` | `INT` | `NOT NULL CHECK (VALUE BETWEEN 100000 AND 999999)` | `玩家.uid`（`P123456`）、`地区.uid`（`R123456`）、`联军.uid`（`C123456`） |
| `权限等级` | `SMALLINT` | `CHECK (VALUE BETWEEN 1 AND 3)`，**可空** | `玩家.联军权限等级`：NULL = 元首/总理（在三级之上）或没有联军 |

`稳定度` 故意不用 `非负计数`——它可以是负数。

**`六位编号` 落库只存 6 位数字，前缀不进库**：`P` / `R` / `C` 是显示与解析时的约定，
库表已经知道自己存的是玩家、地区还是联军，没必要再存一个字母。
命令里必须带前缀（`P123456` / `R123456` / `C123456`），这样解析器一眼能分出找的是哪一个。

> 小坑：`\d 玩家` 里 `uid` 那一行会显示成可空——那是 psql 不展示 DOMAIN 自带的 `NOT NULL`。
> 实际插入 `NULL` 会被拒（`domain "六位编号" does not allow null values`），已实测。

为什么用 DOMAIN 而不是每列各写一遍 CHECK：

- 约束只写一次。加一个计数字段不用再抄一行 `CHECK (… >= 0)`，也不会漏写。
- 语义写在列名右边（`驻军 非负计数`），比 `BIGINT NOT NULL DEFAULT 0 CHECK (…)` 好读得多。
- 改约束用 `ALTER DOMAIN … ADD CONSTRAINT`，不用动几十张表。

已验证（2026-10-29）：sqlx 0.8.6 读写 DOMAIN 列正常——PostgreSQL 在结果集描述里报的是
**底层类型**，`i64` 照样解得出来，`query_as` 不需要任何 cast。

> DOMAIN 定在 [`01_domains.sql`](../crates/storage/migrations/01_domains.sql)。

### 4.1 `玩家`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键，不对外暴露 |
| `uid` | `六位编号` | `UNIQUE` | **秘密凭证**，显示为 `P123456`；落库只存 6 位数字 |
| `工人` | `非负计数` | | 从事生产的人口 |
| `私军` | `非负计数` | | **操作兵器的兵员**，与工人争抢同一批人口 |
| `地下工人` | `非负计数` | | 分配在地下工厂的工人，空袭炸不到 |
| `休假工人` | `非负计数` | | 暂时不生产的工人 |
| `科技` | `非负计数` | | 解锁军备的门槛（等级） |
| `生产技术` | `非负计数` | | 产量乘数；原版"改进生产技术"，消耗生活资料升级 |
| `厂房` | `非负计数` | | 产能上限；原版"扩建厂房"，消耗钢铁 |
| `地下工厂投入` | `非负计数` | | 地下工厂的累计投入，够阈值才有地下产能 |
| `科技池投入` | `非负计数` | | 投进科技池的资源，攒满换一级科技 |
| `科技池容量` | `非负计数` | | 科技池的容量上限 |
| `生产次数` | `非负计数` | | 可积攒的生产次数：**每小时 +1、上限 8**，没次数不能生产（全服定时任务推进） |
| `军事行动点` | `非负计数` | | 发动攻击、枚举地区要花；怎么恢复待定 |
| `稳定度` | `BIGINT` | `NOT NULL DEFAULT 50` | **可以为负**；负值不能生产 |
| `工资` | `非负计数` | | 高于基准提升稳定度 |
| `上次签到时间` | `可空时间戳` | | NULL = 从没签到 |
| `今日招募数量` | `非负计数` | | 今天已经招了多少（每日总量有上限，0 点由定时任务清零） |
| `上次炮击时间` | `可空时间戳` | | 炮击冷却 |
| `上次驻扎时间` | `可空时间戳` | | 驻扎冷却的锚点，防止刚撤走就驻扎到别处 |
| `驻扎地区_id` | `BIGINT` | `NULL` | 逻辑引用 `地区.id`；弱引用，地区易主不影响 |
| `联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id` |
| `联军职务` | `TEXT` | `NULL` | `leader`（元首）/ `premier`（总理）/ `officer`（干部）/ `member`（成员）；**与 `联军_id` 同生共死** |
| `联军权限等级` | `权限等级` | `NULL` | 1–3 级；元首与总理**在三级之上**，所以为 `NULL`；干部与成员必须有等级 |
| `联军贡献` | `非负计数` | | 对当前联军的贡献；**入盟时清零**，退盟后无意义 |
| `加入联军时间` | `可空时间戳` | | NULL = 没入盟 |
| `出生保护至` | `可空时间戳` | | `NULL` = 已过保护 |
| `创建时间` | `时间戳` | | |

索引：`玩家 (联军_id)`、`玩家 (驻扎地区_id)`（后者用于"这个地区驻着谁"），
`uid` 的唯一约束自带索引。另有两条**部分唯一索引**保证一个联军只有一个元首、一个总理：

```sql
CREATE UNIQUE INDEX 玩家_联军元首唯一 ON 玩家 (联军_id) WHERE 联军职务 = 'leader';
CREATE UNIQUE INDEX 玩家_联军总理唯一 ON 玩家 (联军_id) WHERE 联军职务 = 'premier';
```

> **`联军职务` 与 `联军权限等级` 都可以为 `NULL`**，但含义不同：
>
> | 情况 | `联军_id` | `联军职务` | `联军权限等级` |
> |---|---|---|---|
> | 没有联军 | `NULL` | `NULL` | `NULL` |
> | 元首 / 总理 | 有 | `leader` / `premier` | `NULL`（在三级之上，不需要等级） |
> | 干部 / 成员 | 有 | `officer` / `member` | `1`–`3` |
>
> 这条由 `CHECK` 强制（约束名 `联军职务与等级一致`），所以"没联军"再也不会和
> "是成员"变成同一个值（旧版是 `NOT NULL DEFAULT 'member'`）。
>
> 为什么职务与等级都放玩家行、不放联军表：v2 在 `CoalitionArmy` 里存 `联军元首: string`
> 与四个 `…权限成员列表` 数组，改一次职务要读改写整个数组；这里一行玩家就是一份成员数据，
> 唯一性由索引兜底，不需要"读出来看一眼再写回去"（D35 / D37）。

**签到用时间戳，招募用计数器**：

- 签到是"每天一次、奖励固定"，一个 `上次签到时间` 就能回答"今天签了没"，
  判定 `now - 上次 >= 1 天`，不依赖任何定时任务。
- 招募是"每天有总量上限、玩家自选每次招多少"，时间戳回答不了"还能招多少"，
  所以必须存 `今日招募数量`，由**全服 0 点批处理**清零（D32）。
- 生产次数同理：每小时 +1、上限 8，由全服批处理推进，所以**不存"上次结算时间"**。

> 资源和装备**不在本表**，都在 `库存`（所有者类型 = `player`）。
>
> 本表**没有 `名称` 列**：玩家以平台账号为身份，游戏里靠 `@`、`P…` 编号或平台账号 id 寻址，
> 不存"指挥官名"（见 [design.md 第五节](./design.md)、[protocol.md mentions](./protocol.md)）。
>
> `uid` 是**秘密**：知道 `P123456` 才能在别的群找到这个人，和地区的 `R123456` 同一套规则（D30）。
>
> `联军贡献` 放这里而不是联军表里：一个玩家同时只在一个联军，所以"成员数据"天然是
> 玩家行的一部分；查贡献一次查询直达，不用先查联军再查成员表（D33）。

### 4.2 `联军`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `uid` | `六位编号` | `UNIQUE` | **对外的公开编号**，显示为 `C123456`；不保密，不授予任何权限 |
| `名称` | `TEXT` | `NOT NULL UNIQUE` | 玩家自填，需要审核（见下） |
| `名称是否审核` | `BOOLEAN` | `NOT NULL DEFAULT TRUE` | `FALSE` ⇒ 显示成 `***`；v1 没有审核后台，默认视为通过 |
| `政治体制` | `TEXT` | `NOT NULL DEFAULT 'democracy'` | `democracy` / `authoritarian` / `totalitarian`；决定每个动作的默认权限阈值 |
| `首都_地区_id` | `BIGINT` | `NULL` | 逻辑引用 `地区.id`；必须是自己控制的地区（不变量，DB 管不了跨表） |
| `宣称人口` | `非负计数` | | **公开**的人口数字，玩家自己填；实际人口是派生值（见下） |
| `宣称兵力` | `非负计数` | | **公开**的兵力数字，玩家自己填；实际兵力就是 `联军军队` |
| `联军军队` | `非负计数` | | 共享兵员，**实际兵力**（只对成员可见）；**驻军的唯一来源** |
| `扩军计划` | `非负计数` | | 每天允许转入联军军队的兵力上限；**0 = 未设置（禁止转入）** |
| `当天扩军累计` | `非负计数` | | 今天已经转入多少兵；每天 0 点由全服定时任务清零 |
| `税率` | `百分比` | | 成员生产利润上缴比例（0–100），上缴部分进联军仓库 |
| `当天资本增量` | `非负计数` | | 今天成员**生产利润的合计**（生活资料计）；每天 0 点日结落一行再清零 |
| `上次改名时间` | `可空时间戳` | | 改名冷却与审核的锚点；`NULL` = 建好还没改过 |
| `创建时间` | `时间戳` | | |

> **宣称 ≠ 实际。** 联军对外只有一个数字：`宣称人口` / `宣称兵力`，是**成员自己填**的，
  别人（外邦、排行榜、战报）看到的也是它——所以它可以吹牛。
> 实际值不在对联军的公开查询里：
>
> | | 公开（谁都能看） | 保密（只有成员能看） |
> |---|---|---|
> | 人口 | `宣称人口`（自填） | `SUM(成员.工人 + 私军 + 地下工人 + 休假工人)` —— **实际人口** |
> | 兵力 | `宣称兵力`（自填） | `联军.联军军队` —— **实际兵力** |
>
> 实际人口是**成员总人口之和**（D39 修正 D38 的"只数工人"口径），派生不落列；
> 实际兵力本来就是 `联军军队`。
> 两者都只在对内查询（`我的联军`）里出现——这是"联军内部信息"的边界，
> 和 `P…` / `R…` 是秘密凭证是两回事：这里藏的是**真实实力**，不是访问权限。

#### 4.2.1 从 v2 `CoalitionArmy` 迁过来的字段，哪些**没有**变成列

v2 的 `CoalitionArmy` 有 29 个字段，落库的只有上面 15 列。剩下的不是漏了，是**换了存法**：

| v2 字段 | 我们怎么存 | 为什么 |
|---|---|---|
| `联军编号` | `uid`（`C123456`） | v2 是 sqids 字符串；我们统一 6 位数字 |
| `联军元首` / `联军总理` | `玩家.联军职务 = 'leader' / 'premier'` | 一人一职，玩家行就是成员数据；唯一性由部分唯一索引保证（D35） |
| `联军四级 / 三级 / 二级 / 一级权限成员列表` | `玩家.联军权限等级` 一列（1–3） | 四个数组是"每个成员一个等级"的文档库写法；关系库里一人一个数，阈值由 `(政体, 动作)` 常量表决定（D37） |
| `联军成员数量` | `COUNT(*) WHERE 联军_id = ?` | 计数器是文档库没有 join 时的替代品 |
| `联军成员列表` | `WHERE 联军_id = ?`（贡献与加入时间在玩家行） | 同上，且 D33 已经把成员数据放在玩家行 |
| `联军地区列表` | `WHERE 控制方_联军_id = ?` | 同上 |
| `联军生活资料` | `库存(所有者类型 = 'coalition', 物品 = 'resource:food')` | 联军有完整仓库，不是只存一种物资 |
| `生活资料分配记录` | 表 `联军分配记录` | JSON 数组没法分页、没法按接收方索引 |
| `联军宣称人口` / `联军宣称兵力` | 两列 `宣称人口` / `宣称兵力`（玩家自己填的公开数字） | v2 里它们建好联军写 0 就再没被更新过，是个没接线的字段；现在给它明确语义：这是**对外宣称**的数字，不是实际值 |
| `当天内资本增量` | `当天资本增量` | 一样，只是改个短名 |
| `三天内 / 七天内资本增量`、`资本增量历史记录` | 表 `联军资本增量`（每天一行）+ 窗口 `SUM` | 滚动列会和历史数组对不上；窗口聚合只有一个真相 |
| `联军名称` | `名称` | |
| `名称是否审核` | 同名 | |
| `建立日期` / `上次改名日期` | `创建时间` / `上次改名时间` | 日期一律 Unix 秒 |
| `扩军计划` / `当天扩军累计` | 同名 | |

> 一句话：**存状态，不存派生值；JSON 数组拆成表。**

#### 4.2.2 `联军分配记录`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `联军_id` | `BIGINT` | `NOT NULL` | 逻辑引用 `联军.id` |
| `分配者_玩家_id` | `BIGINT` | `NOT NULL` | 谁批的这笔 |
| `接收方_玩家_id` | `BIGINT` | `NOT NULL` | 谁收的这笔 |
| `物品` | `TEXT` | `NOT NULL` | 物品编码（如 `resource:food`），不加 CHECK |
| `数量` | `非负计数` | | |
| `时间` | `时间戳` | | |

索引：`联军分配记录 (联军_id, 时间 DESC)` —— `分配记录` 指令就是取最近 N 条。

> 记"谁给谁"而不是只记数字：分配是**有对象**的行为（v2 的 `AssignRecord` 也是
> 分配者/接收方/数量/时间四项）。物资本身走 `库存`，这张表只留流水。

#### 4.2.3 `联军资本增量`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `联军_id` | `BIGINT` | `NOT NULL` | 逻辑引用 `联军.id` |
| `日结时间` | `时间戳` | | 这一行结算的是哪一天的**日界**（UTC+8 零点）的 Unix 秒 |
| `资本增量` | `非负计数` | | 那天成员生产利润的合计（**不是税收**，见下） |

主键 `(联军_id, 日结时间)`：

- **一天一行、重跑幂等**：日结重跑会撞主键，不会写出两行。
- **三天 / 七天就是窗口 SUM**：`WHERE 日结时间 > now - 3 * 86400`，不需要三列滚动值。
- **`日结时间` 不用 `DATE`**：`DATE` 会把"几点算今天"藏进列类型里，而我们只有
  "UTC+8 零点"这一个定义（第四节、`系统状态`）。

> **口径**：`资本增量` 记的是"利润"（生产产出 − 工资），**与税率无关**。
> 税率只决定利润里多少进联军仓库，改税率不该让历史 GDP 跳变。
> 这个口径来自 v2（`记录联军资本增量(联军编号, 利润, 联军税额)` 里第一个参数是利润），
> 同一个数也决定成员的 `联军贡献`（v2 里 `累计联军成员贡献(…, 利润)`）。

### 4.3 `地区`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键 |
| `uid` | `六位编号` | `UNIQUE` | **对外访问凭证**，显示为 `R123456`，落库只存 6 位数字 |
| `名称` | `TEXT` | `NOT NULL` | |
| `控制方_联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id`；`NULL` = 无主 |
| `驻军` | `非负计数` | | 从联军军队转化而来 |
| `创建时间` | `时间戳` | | |

索引：`地区 (控制方_联军_id)`。

> **`控制方` 与 `驻军` 恒等价**：`驻军 > 0 ⇔ 控制方 IS NOT NULL`。
> 见第六节不变量。
>
> **为什么 `uid` 不是主键**：主键对内、要参与 join 和索引；`uid` 是对外的秘密。
> 两者混用会让"换一次凭证 = 改一遍所有关联行"，且秘密会顺着每个引用泄露。
>
> **`uid` 是随机的，不是自增的**：从 id 推不出 uid（否则"秘密"就没意义了）。
> 生成时撞了就重试（90 万个号，2 人规模撞不到）。

### 4.4 `地区建筑`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `地区_id` | `BIGINT` | `NOT NULL` | |
| `建筑` | `TEXT` | `NOT NULL` | 建筑编码，见 [catalog.md 第三节](./catalog.md#三建筑编码)；清单待定 |
| `完成度` | `百分比` | | `0..=100` |

主键：`(地区_id, 建筑)`。`0..=100` 的约束来自 `百分比` 这个 DOMAIN，不单独写 CHECK。

> ✅ **一种建筑在一个地区只有一份**，用 **0–100 的完成度**表示进度，到阈值才解锁效果。
> 原版就是这样：学校完成度 60% 才能"城市招募工人"，炼钢厂 70% 才能炼钢。
>
> ✅ **不做"建筑定义总表"**。建筑挂在地区下，表里只存"哪个地区、哪种建筑、建到几成"。
> 清单短、且效果要参与规则计算，所以效果与阈值写成 `domain` 里的常量（能 `match` 穷尽）；
> 真到几十种再改成数据驱动，`建筑` 是 `TEXT`，不需要迁移。
>
> ❓ 清单、阈值、造价未定，见 [design.md](./design.md)。
>
> 索引：主键已覆盖"查一个地区的全部建筑"（`地区_id` 是前导列）。

### 4.5 `平台绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `玩家_id` | `BIGINT` | `NOT NULL` | 逻辑引用 `玩家.id` |
| `平台` | `TEXT` | `NOT NULL` | `onebot` / `discord` / `telegram`；不认识的平台被拒绝 |
| `平台_uid` | `TEXT` | `NOT NULL` | 平台侧用户 id |
| `绑定时间` | `时间戳` | | |

两条唯一约束，缺一不可：

- `UNIQUE (平台, 平台_uid)` —— **对外**：一个平台账号只能属于一个玩家（登录时按它查）。
- `UNIQUE (玩家_id, 平台)` —— **对内**：一个玩家在同一个平台只能有一个账号。
  少了它，同一个人两个 QQ 号都能登同一个玩家，而"这个玩家现在用哪个号说话"没有答案。

不额外建索引：两条唯一约束自带的索引正好覆盖两个查询方向
（`(平台, 平台_uid)` 查登录、`(玩家_id, 平台)` 列身份）。

> ✅ **一个玩家可以有 1..N 个平台账号**，这是"跨平台同一身份"的实现。
> 但**绑定不是合并**：只有还没注册过的平台账号才能被绑；已经是一个玩家的账号，拒绝绑给别人。
> 因为不存在"两个号合并成一份资源"，也就不需要定义资源相加的规则（见 [decisions.md D23](./decisions.md)）。
>
> ❓ v1 不做解绑：绑错了只能手改库。等真有人需要再补指令。

### 4.6 `地区频道绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `地区_id` | `BIGINT` | `NOT NULL` | |
| `平台` | `TEXT` | `NOT NULL` | |
| `频道_id` | `TEXT` | `NOT NULL` | 群 / 频道 id |
| `绑定时间` | `时间戳` | | |

约束：`UNIQUE (平台, 频道_id)` —— 一个频道只能属于一个地区。
反向**不唯一**：一个地区可以绑多个频道（这正是跨平台共享的实现方式）。
索引：`地区频道绑定 (地区_id)`（列一个地区绑了哪些频道）。

### 4.7 `系统状态`

单行表，只放"全服定时结算推进到哪了"。`id` 恒为 `1`（`CHECK (id = 1)`）。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `SMALLINT` | `PRIMARY KEY DEFAULT 1 CHECK (id = 1)` | 单行 |
| `上次生产结算` | `可空时间戳` | | 生产次数结算到哪一刻；NULL = 还没结算过 |
| `上次日结` | `可空时间戳` | | 招募数量上次清零的时刻 |

为什么需要它：每小时 +1 生产次数、每天 0 点清零招募数量都是**全服批处理**。
进程在结算点没跑（部署、崩溃、重启）就会漏一次——漏一次就是玩家少攒一次次数，
或者一整天不能招募。有了这两个时间戳，启动时能一次性补算：

```sql
-- 补 N 小时，一条 SQL 覆盖全服，不用逐玩家算
UPDATE 玩家 SET 生产次数 = LEAST(8, 生产次数 + $1);
UPDATE 系统状态 SET 上次生产结算 = 上次生产结算 + $1 * 3600 WHERE id = 1;
```

代价是"全服状态"和"玩家状态"分成两处，读的时候要一起看；但比给每个玩家存两个锚点便宜得多
（D32 记录了这次取舍）。

## 五、领域类型（`domain`）

### 5.1 标识与时间用 newtype

```rust
/// 玩家主键。
pub struct 玩家Id(pub i64);

/// 联军主键。
pub struct 联军Id(pub i64);

/// 地区主键（内部 id，不是对外的 uid）。
pub struct 地区Id(pub i64);

/// Unix 秒。
pub struct 时间(pub i64);

/// 玩家对外的秘密编号，显示为 `P123456`。
///
/// 和 `玩家Id` 是两个东西：`玩家Id` 是内部主键（会出现在日志、索引、join 里），
/// `玩家Uid` 是给玩家看的凭证，**不得进日志、不得出现在公开输出里**。
pub struct 玩家Uid(pub i32);

/// 地区对外的秘密编号，显示为 `R123456`。
pub struct 地区Uid(pub i32);

/// 联军对外的**公开**编号，显示为 `C123456`。
///
/// 和上面两个不同：它不是凭证，出现在排行榜、战报、`我的联军` 里都没问题——
/// 知道它既找不到人，也打不了地区。
pub struct 联军Uid(pub i32);

/// 建筑编码，落库值（如 `school`）。
///
/// 清单定稿后换成 `enum 建筑`，DB 里的 `TEXT` 值不变——
/// 在枚举定稿前先留一个 newtype，避免规则代码到处传裸 `String`。
pub struct 建筑编码(pub String);
```

三个编号 newtype 的载体是 `i32` 不是 `u32`：PG 的 `INT` 是**有符号**类型，
`u32` 在 `sqlx` 里没有 `Type` 实现，每次绑定 / 读取都得做一次被 lint deny 的符号转换；
而六位编号（`100000..=999999`）完整落在 `i32` 里。
`domain::编号` 已按 `i32` 提供三个前缀常量与 `显示`（S2 已实现）；
`玩家Uid` 等 newtype **随实体类型落地**——现在还没有函数收"编号"作参数，
先造三个空壳只会让代码到处拆包。

### 5.1.1 枚举与编码

`物品`、`装备`、`建筑` 的变体与落库编码见 [catalog.md](./catalog.md)。写法固定成一对：

```rust
impl 物品 {
    pub const fn 编码(&self) -> &'static str;
    pub fn 解析(s: &str) -> Option<Self>;
}
```

两个方向都要有测试（`解析(编码(x)) == x`），否则改一个字母就会在运行期变成"数据损坏"。
`storage` 用 `解析` 做 `TryFrom`，**未知编码一律当数据损坏**，不要 fallback 成某个默认值。

理由：四个参数全是 `i64` 的函数，早晚会把 `玩家Id` 和 `联军Id` 传反，编译器不会吭声。

### 5.2 实体

```rust

    pub 联军职务: Option<联军职务>,

    pub 名称是否审核: bool,
    pub 政治体制: 联军政体,
    /// 首都；`None` = 还没设。
    pub 首都: Option<地区Id>,

    // 对外宣称（公开），实际值不在这里：人口要 SUM 成员，兵力就是 联军军队
    pub 宣称人口: i64,
    pub 宣称兵力: i64,

    // 兵
    pub 联军军队: i64,

    pub 扩军计划: i64,
    pub 当天扩军累计: i64,

    // 财政
    /// 0..=100，上缴比例。
    pub 税率: u8,
    pub 当天资本增量: i64,

```

> **物资不在 `玩家` 里**：生活资料、钢铁、石油、装备……全在 `库存`。

/// 地区。
pub struct 地区 {
    pub id: 地区Id,

    pub 名称: String,
    pub 控制方: Option<联军Id>,

### 5.4 跨实体聚合：`战场快照`

战争一次要读**玩家 + 联军 + 库存**三处，攻陷地区还多读一张地区表。
domain 不查库，所以 `server` 负责把这些读出来拼成一个值传进去：

```rust
/// 一次战争结算所需的全部输入。
pub struct 战场快照 {
    pub 攻方: 玩家,
    pub 攻方库存: 库存,
    pub 守方: 玩家,
    pub 守方库存: 库存,
    pub 守方联军: Option<联军>,
    pub 现在: 时间,
}
```

攻陷地区另有一个更小的快照（攻方库存 + 地区 + 攻方联军）。

## 六、不变量

这些是**任何操作都必须维持**的性质。domain 的每个函数返回前都应保证它们成立：

| 不变量 | 说明 |
|---|---|
| `工人 + 私军 + 地下工人 + 休假工人 = 总人口` | 扩军是"工人 → 私军"，**1:1**；私军阵亡 = 人口永久损失 |
| `工人 >= 0`、`私军 >= 0` | |
| `联军军队 >= 0`、`驻军 >= 0` | 驻军从联军军队转化，不能凭空出现 |
| `驻军 > 0 ⇔ 控制方 IS NOT NULL` | 无主地区不可能有驻军；驻军被打光即易主 |
| `玩家.联军_id IS NULL` ⇔ `联军职务` 与 `联军权限等级` 都是 `NULL` | 由 DB 的 CHECK `联军职务与等级一致` 保证：没有联军就没有职务与等级 |
| 元首/总理的 `联军权限等级` 是 `NULL`；干部/成员必须是 `1`–`3` | 同上，一条 CHECK 说清"职务在三级之上"这件事 |
| `玩家.联军权限等级` ∈ `[1, 3]` | 来自 `权限等级` 这个 DOMAIN |
| 每个联军至多一个元首、一个总理 | 由部分唯一索引保证；**至少**一个元首只能由应用层保证（人走了要有人接班） |
| `联军.首都` 是本联军控制的地区 | 跨表不变量，DB 管不了；`NULL` = 还没设首都 |
| `联军.税率` ∈ `[0, 100]` | 来自 `百分比` 这个 DOMAIN |
| `联军.当天扩军累计 ≤ 联军.扩军计划`（`扩军计划 > 0` 时） | 扩军计划是每日上限，日结清零累计 |
| `联军资本增量` 每天每联军至多一行 | 主键 `(联军_id, 日结时间)` |
| 实际人口只对成员可见 | `SUM(成员.工人 + 私军 + 地下工人 + 休假工人)` 是派生值；对外只能给 `宣称人口` |
| 实际兵力只对成员可见 | 就是 `联军军队`；对外只能给 `宣称兵力` |
| `玩家.uid` ∈ `[100000, 999999]` 且唯一 | 随机生成，**从 `id` 推不出来**；是秘密凭证 |
| `地区.uid` ∈ `[100000, 999999]` 且唯一 | 同上，显示为 `R…` |
| `联军.uid` ∈ `[100000, 999999]` 且唯一 | 同上，显示为 `C…`；**公开**，可出现在排行榜与战报里 |
| `玩家.生产次数` ∈ `[0, 8]` | 每小时 +1，攒满 8 就停；没次数不能生产（全服定时任务推进） |
| `玩家.今日招募数量` ≤ 每日上限 | 每天 0 点由全服定时任务清零 |
| `玩家.联军贡献` 只在 `联军_id IS NOT NULL` 时有意义 | 入盟清零、退盟归零 |
| 库存数量 `>= 0` | 任何扣减前先校验 |
| `地区建筑.完成度` ∈ `[0, 100]` | v1 没有建筑破坏机制，完成度只增不减 |
| `平台绑定.平台账号` 唯一 | `(平台, 平台_uid)` 唯一：一个平台账号只属于一个玩家 |
| `平台绑定.玩家身份` 唯一 | `(玩家_id, 平台)` 唯一：一个玩家在同一个平台只有一个账号 |
| 绑定只能落在"还没有玩家"的账号上 | 已有玩家的平台账号不能被绑给别人——这正是"不需要合并规则"的前提 |

## 七、存储映射（`storage`）

- 行类型 `玩家行` / `联军行` / `地区行`：`#[derive(sqlx::FromRow)]`，只在 `storage` 内部可见，绝不带 `Serialize`。
- 领域类型：`domain::玩家` 等，**绝不带 `FromRow`**。
- 两者之间用 `TryFrom<玩家行> for 玩家` 转换，转换失败 = 数据损坏，返回内部错误。
- 库存：`库存行` 的多行聚合成 `库存`，在 `storage` 里做完。

## 八、已定与待定

### 8.1 已定（截至 2026-10-30）

1. **玩家身上、联军仓库、地区仓库都能存东西**——`库存` 的三种所有者同时成立，
   没有"物资只能放某一处"的限制。区别只在"谁能访问"（见 3.2），不在机制。
2. **v1 有建筑**，挂**地区**下（不挂玩家、不挂联军），一种建筑一份，
   进度用 **0–100 完成度**表示；不做"建筑定义总表"（理由见 4.4）。
3. **库存按所有者整体读写**：一次查出该所有者的全部物品，规则算完再写回变化的行。
   单物品零散查会让一次掠夺变成 N 次往返，且中途失败会留下"搬了一半"的状态。
4. **一个玩家 = 1..N 个平台账号**，用 `平台绑定` 行存，不用"每个平台一列"
   （v2 的 `onebot` / `discord` / `telegram` 三列）——加平台不该改表结构。
5. **注册是显式的**：发 `注册` 才建玩家。自动注册会把每个平台账号都变成玩家，
   "这个账号还没注册"这个前提就永远不成立，绑定也就无从发起。
6. **绑定不是合并**：只允许把还没有玩家的平台账号挂到已有玩家上。
7. **`玩家` 的字段集合照 v2 的 `Player`**，但物资走 `库存`、时间走时间戳、
   地区引用走 `地区_id`（见 [D28](./decisions.md)）。
8. **玩家和地区都有 6 位秘密编号**：玩家显示 `P123456`、地区显示 `R123456`，
   落库只存数字（D30）。uid 是凭证不是编号，不能当主键。
9. **v1 有地下工厂 / 地下工人 / 休假工人 / 科技池 / 生产次数**：
   `生产次数` 每小时 +1、上限 8，没次数不能生产；招募按"每日总量"算，
   所以需要 `今日招募数量` 计数器（D31）。
10. **`上次驻扎时间` 用来拦住"刚撤走就跳到别处"**，是驻扎冷却的锚点。
11. **全服定时结算**：生产次数与招募清零靠批处理，进度存在单行表 `系统状态` 里，
    漏跑能补算（D32）。
12. **军事行动点挂在玩家表**；**贡献挂在玩家行上的 `联军贡献`**，入盟清零（D33）。
13. **`联军` 照 v2 的 `CoalitionArmy` 落字段**：成员列表 / 地区列表是派生值不落列，
    `生活资料分配记录` 与 `资本增量历史` 拆成两张表（D34）。
14. **元首与总理落在 `玩家.联军职务` 上**，一个联军各只有一个，部分唯一索引兜底（D35）。
15. **联军也有编号，但是公开的 `C…`**：只用于查询与展示，不授予任何权限（D36）。
16. **联军权力分三级**，`玩家.联军权限等级` 存 1–3；元首与总理**在三级之上**，
    所以没有等级（`NULL`），能做任何事（D37）。
17. **宣称与实际分开**：`联军.宣称人口/宣称兵力` 是成员自填的**公开**数字；
    实际人口 = 所有成员的总人口之和（工人 + 私军 + 地下工人 + 休假工人，D39）、
    实际兵力 = `联军军队`，只对成员可见（D38）。

### 8.2 仍然待定（不阻塞表结构，只影响 S4 之后的规则）

1. **建筑清单、每种的效果与解锁阈值** —— 玩法问题，记在 [design.md](./design.md)。
2. **修建的资源消耗与推进方式** —— 一次扣费推进若干完成度，还是随真实时间推进？
3. **地区仓库要不要设容量上限** —— 如果要，容量就是建筑「仓库」完成度的效果，
   而不是 `地区` 表上加一列。
4. **军事行动点怎么恢复** —— 列已经在 `玩家` 上，但恢复模型（自然恢复 / 消耗换）
   还没定，见 [design.md 2.2](./design.md)。
5. **贡献的加减规则** —— v2 的口径是"每生产一次，`联军贡献 += 税前利润`"（与
   `当天资本增量` 同源），照搬即可；"除生产之外还有哪些行为加贡献"仍未定。
   `贡献排名` 按联军内排序。
6. **联军的权限机制** —— 形状已经定了（三级 + 职务在其上），**还差每个动作的阈值**：

   ```text
   玩家.联军权限等级        1..=3，一条列（元首/总理为 NULL）
   (政体, 动作) -> 最低等级  domain 里的常量表，不落库（D37）
   ```

   剩下的活：v1 有哪几个动作要判定、每个动作在三种政体下要求几级。
   **这两件事等实现具体指令时再定**（每个动作实现时顺手写进常量表），
   不在建表阶段拍脑袋。
7. **政体阈值与升降级** —— 政体只影响阈值（极权制更严），这是玩法，v1 保留。
   但"贡献变了之后要不要自动升降级"（v2 每小时权力检测）还没定：
   v1 可能只留"元首手动任命"，自动检测以后再说。
8. **解散联军** —— 现在没有这一列，也没有这条指令。真要做就加 `解散时间 可空时间戳`
   （删除行会让 `C…` 编号被回收，违反"编号不重复"）。
9. **改名规则与审核流程** —— `名称是否审核` 这一列和 `上次改名时间` 已经就位，
   但"多久能改一次、谁审、没审过显示什么"还没定。v1 默认视为通过。
10. **没有军衔制** —— v1 的军队没有建制（见 [design.md 3.1](./design.md)），
    所以 v2 的 `军衔表(联军编号, 玩家UID, 军衔等级)` 不搬。指挥权限就是三级权限本身。
