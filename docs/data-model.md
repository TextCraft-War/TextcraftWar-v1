# 数据模型

> 状态：**草案，待作者确认** ｜ 最后更新：2026-10-29
>
> 本文是**表结构与领域类型的唯一事实来源**。`storage`/`domain` 的文档只写实现细节，不再重复定义。
> 玩法规则见 [design.md](./design.md)。

## 一、建模约束

这五条适用于所有表，后面不再逐条重复：

1. 表名、列名用中文；SQL 里必须加双引号（`"玩家"`）。
2. 所有时间列是 `BIGINT`，存 **Unix 秒**。不用 `TIMESTAMP`——跨时区、跨平台，整数最省事。
3. **不建物理外键。** 全部是逻辑引用，一致性由应用层的事务保证。
   原因：联军会解散、地区会易主，物理外键的级联语义在这里全是错的。
4. 枚举列一律存 `TEXT`（英文小写），读出后在 `storage` 里 `TryFrom` 成领域枚举。
5. 一表一实体，不搞宽表。

## 二、关系

```
玩家 ──┬──< 平台绑定        (一个玩家可绑多个平台账号)
       ├──< 库存            (所有者 = 玩家)
       └──> 联军            (可空：新玩家没有联军)

联军 ──< 地区               (控制方，可空：无主地区)
     └──< 库存            (所有者 = 联军)

地区 ──┬──< 地区频道绑定     (一个地区可绑多个频道，跨平台)
       ├──< 库存            (所有者 = 地区，即"地区仓库")
       └──< 地区建筑         (建筑挂地区下)
```

## 三、库存：一张表管所有物品

**这是本文档最重要的一个决定。**

玩家的背包、联军的仓库、地区的仓库，是**同一个机制**：某处存着若干种物品各多少个。
所以只用一张 `库存` 表，用 `所有者类型 + 所有者_id` 区分归属。

```sql
库存(所有者类型 TEXT, 所有者_id BIGINT, 物品 TEXT, 数量 BIGINT)
主键 (所有者类型, 所有者_id, 物品)
```

好处：

- **掠夺就是"改两行库存"**，不管是从玩家搬还是从地区仓库搬，代码是同一个函数。
- 加一种物品不用改任何表结构。
- "地区仓库比身上安全"这条玩法，就是"同一张表里，地区那一行的 uid 更难拿到"。

代价：读一个玩家的资源要多一次查询（或一次 join）。2 人规模下可以忽略。

### 3.1 物品枚举

```rust
/// 库存里能放的东西。
pub enum 物品 {
    生活资料,
    世界货币,
    装备(装备),
}
```

落库编码（带前缀，避免不同类别重名）：

| 物品 | DB 值 |
|---|---|
| 生活资料 | `resource:food` |
| 世界货币 | `resource:money` |
| 某种装备 | `equipment:warship` 之类 |

### 3.2 三类所有者的语义

| 所有者 | 含义 | 谁可以访问 |
|---|---|---|
| 玩家 | 随身物资，**最不安全**（打玩家不需要 UID） | 本人 |
| 联军 | 联军仓库 | 联军成员（v1 仅元首） |
| 地区 | 地区仓库，**最安全**（需要地区 UID 才能打） | 有权限的联军成员 |

## 四、表定义

### 4.1 `玩家`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键，不对外暴露 |
| `工人` | `BIGINT` | `NOT NULL DEFAULT 0` | 从事生产的人口 |
| `私军` | `BIGINT` | `NOT NULL DEFAULT 0` | **操作兵器的兵员**，与工人争抢同一批人口 |
| `科技` | `BIGINT` | `NOT NULL DEFAULT 0` | 解锁军备的门槛 |
| `稳定度` | `BIGINT` | `NOT NULL DEFAULT 50` | **可以为负**；负值不能生产 |
| `工资` | `BIGINT` | `NOT NULL DEFAULT 0` | 高于基准提升稳定度 |
| `联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id` |
| `联军职务` | `TEXT` | `NOT NULL DEFAULT 'member'` | `member` / `officer` / `leader` |
| `出生保护至` | `BIGINT` | `NULL` | Unix 秒；`NULL` = 已过保护 |
| `创建时间` | `BIGINT` | `NOT NULL` | |

索引：`玩家 (联军_id)`。

> 资源和装备**不在本表**，都在 `库存`（所有者类型 = 玩家）。

### 4.2 `联军`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `名称` | `TEXT` | `NOT NULL UNIQUE` | |
| `联军军队` | `BIGINT` | `NOT NULL DEFAULT 0` | 共享兵员，**驻军的唯一来源** |
| `创建时间` | `BIGINT` | `NOT NULL` | |

### 4.3 `地区`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 内部主键 |
| `uid` | `INT` | `NOT NULL UNIQUE` | **对外访问凭证**，6 位数字，保密 |
| `名称` | `TEXT` | `NOT NULL` | |
| `控制方_联军_id` | `BIGINT` | `NULL` | 逻辑引用 `联军.id`；`NULL` = 无主 |
| `驻军` | `BIGINT` | `NOT NULL DEFAULT 0` | 从联军军队转化而来 |
| `创建时间` | `BIGINT` | `NOT NULL` | |

索引：`地区 (控制方_联军_id)`。

> **`控制方` 与 `驻军` 恒等价**：`驻军 > 0 ⇔ 控制方 IS NOT NULL`。
> 见第五节不变量。
>
> **为什么 `uid` 不是主键**：主键对内、要参与 join 和索引；`uid` 是对外的秘密。
> 两者混用会让"换一次凭证 = 改一遍所有关联行"，且秘密会顺着每个引用泄露。

### 4.4 `地区建筑`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `地区_id` | `BIGINT` | `NOT NULL` | |
| `建筑` | `TEXT` | `NOT NULL` | 枚举，暂未定清单 |
| `数量` | `BIGINT` | `NOT NULL DEFAULT 0` | |

主键：`(地区_id, 建筑)`。

> **v1 的建筑清单待定**（见 [design.md](./design.md)）。表和查询函数先建好，
> 枚举后补——因为 `建筑` 是 `TEXT`，加一种建筑不需要迁移。

### 4.5 `平台绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `玩家_id` | `BIGINT` | `NOT NULL` | |
| `平台` | `TEXT` | `NOT NULL` | `onebot` / `discord` / `telegram` |
| `平台_uid` | `TEXT` | `NOT NULL` | 平台侧用户 id |
| `绑定时间` | `BIGINT` | `NOT NULL` | |

约束：`UNIQUE (平台, 平台_uid)` —— 一个平台账号只能绑一个玩家。
索引：`平台绑定 (玩家_id)`。

### 4.6 `地区频道绑定`

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | |
| `地区_id` | `BIGINT` | `NOT NULL` | |
| `平台` | `TEXT` | `NOT NULL` | |
| `频道_id` | `TEXT` | `NOT NULL` | 群 / 频道 id |
| `绑定时间` | `BIGINT` | `NOT NULL` | |

约束：`UNIQUE (平台, 频道_id)` —— 一个频道只能属于一个地区。
反向**不唯一**：一个地区可以绑多个频道（这正是跨平台共享的实现方式）。

## 五、领域类型（`domain`）

### 5.1 标识与时间用 newtype

```rust
/// 玩家主键。
pub struct 玩家Id(pub i64);

/// 联军主键。
pub struct 联军Id(pub i64);

/// 地区主键（内部 id，不是对外的 uid）。
pub struct 地区Id(pub i64);

/// Unix 秒。
pub struct 时间(pub i64);
```

理由：四个参数全是 `i64` 的函数，早晚会把 `玩家Id` 和 `联军Id` 传反，编译器不会吭声。

### 5.2 实体

```rust
/// 玩家。
pub struct 玩家 {
    pub id: 玩家Id,
    pub 工人: i64,
    pub 私军: i64,
    pub 科技: i64,
    pub 稳定度: i64,
    pub 工资: i64,
    pub 联军: Option<联军Id>,
    pub 联军职务: 联军职务,
    pub 出生保护至: Option<时间>,
}

/// 联军。
pub struct 联军 {
    pub id: 联军Id,
    pub 名称: String,
    pub 联军军队: i64,
}

/// 地区。
pub struct 地区 {
    pub id: 地区Id,
    /// 对外访问凭证：6 位数字，不得出现在任何公开输出里。
    pub uid: u32,
    pub 名称: String,
    pub 控制方: Option<联军Id>,
    pub 驻军: i64,
}

/// 库存：物品 -> 数量。
pub struct 库存(pub std::collections::BTreeMap<物品, i64>);
```

库存提供几个便捷方法，避免规则代码里到处 `unwrap_or(0)`：

```rust
impl 库存 {
    /// 取某种物品的数量，不存在时为 0。
    pub fn 取(&self, 物品: 物品) -> i64;

    /// 增减某种物品；减到负数视为错误。
    pub fn 增(&mut self, 物品: 物品, 数量: i64) -> Result<(), 错误>;
}
```

### 5.3 枚举

```rust
/// 接入的聊天平台。
pub enum 平台 { Onebot, Discord, Telegram }

/// 联军内的职务。v1 只用它判断"能不能驻军"。
pub enum 联军职务 { 成员, 干部, 元首 }

/// 战争器械。v1 只有这些。
pub enum 装备 {
    战斗机,     // 巡逻防空
    轰炸机,     // 空袭
    运输机,     // 掠夺
    重炮,       // 炮击
    防空弹药,   // 消耗品，拦截空袭
    地对空导弹, // 部署在地区
}

/// 库存里能放的东西。
pub enum 物品 {
    生活资料,
    世界货币,
    装备(装备),
}
```

> 指令与事件的枚举由 [design.md 第五节](./design.md) 的指令表派生，不在这里重复列举，
> 避免加一条指令要改两处。

### 5.4 跨实体聚合：`战场快照`

战争一次要读**玩家 + 联军 + 库存**三处，攻陷地区还多读一张地区表。
domain 不查库，所以 `server` 负责把这些读出来拼成一个值传进去：

```rust
/// 一次战争结算所需的全部输入。
pub struct 战场快照 {
    pub 攻方: 玩家,
    pub 攻方库存: 库存,
    pub 守方: 玩家,
    pub 守方库存: 库存,
    pub 守方联军: Option<联军>,
    pub 现在: 时间,
}
```

攻陷地区另有一个更小的快照（攻方库存 + 地区 + 攻方联军）。

## 六、不变量

这些是**任何操作都必须维持**的性质。domain 的每个函数返回前都应保证它们成立：

| 不变量 | 说明 |
|---|---|
| `工人 + 私军 = 总人口` | 扩军是"工人 → 私军"，**1:1**；私军阵亡 = 人口永久损失 |
| `工人 >= 0`、`私军 >= 0` | |
| `联军军队 >= 0`、`驻军 >= 0` | 驻军从联军军队转化，不能凭空出现 |
| `驻军 > 0 ⇔ 控制方 IS NOT NULL` | 无主地区不可能有驻军；驻军被打光即易主 |
| `玩家.联军` 为 `None` ⇒ `联军职务` 无意义 | 默认 `成员`，读取时忽略 |
| `地区.uid` ∈ `[100000, 999999]` 且唯一 | |
| 库存数量 `>= 0` | 任何扣减前先校验 |

## 七、存储映射（`storage`）

- 行类型 `玩家行` / `联军行` / `地区行`：`#[derive(sqlx::FromRow)]`，只在 `storage` 内部可见，绝不带 `Serialize`。
- 领域类型：`domain::玩家` 等，**绝不带 `FromRow`**。
- 两者之间用 `TryFrom<玩家行> for 玩家` 转换，转换失败 = 数据损坏，返回内部错误。
- 库存：`库存行` 的多行聚合成 `库存`，在 `storage` 里做完。

## 八、待确认

1. **`地区建筑` 的清单**：v1 要不要建筑？如果不要，这张表先空着还是干脆不建？
2. **联军仓库能不能放装备**：现在所有者的库存是通用的，联军仓库天然能放，但 v1 要不要开放"联军分配装备"。
3. **库存的读写粒度**：单个物品一次一查，还是整个所有者一次读全（推荐后者，2 人规模一次读空）。
