# server — WebSocket 服务器

> 状态：施工中（尚无实现）｜ 最后更新：2026-10-29
>
> 契约见 [docs/protocol.md](../../../docs/protocol.md)；分层见 [architecture.md](../../../docs/architecture.md)。

## 一、这个 crate 是什么

命令外壳。它做四件事：

1. 收 WS 消息，解 JSON
2. 把文本解析成指令
3. 调 `domain` 算规则，调 `storage` 落库（**开事务**）
4. 把结果渲染成玩家可见文本，发回去

它**不写规则**，也**不写 SQL**。

## 二、启动序列

```
读配置（环境变量）
  → 建 PgPool
  → sqlx::migrate!().run(&pool)      建表 / 升级表
  → axum::serve(监听地址, 路由)
```

顺序是有意义的：**迁移在绑定端口之前**。库连不上或迁移失败就直接启动失败，
不要出现"端口开着但所有指令都报错"的半死状态。
（`domain` 的数值常量编译进代码，没有运行时"定义表"要加载——见 decisions.md D16/D17。）

配置项（v1，全部走环境变量）：

| 变量 | 说明 |
|---|---|
| `DATABASE_URL` | PostgreSQL 连接串 |
| `BIND_ADDR` | 监听地址，默认 `0.0.0.0:8080` |
| `WS_TOKEN` | 握手共享密钥 |
| `RUST_LOG` | `tracing` 过滤 |

## 三、连接处理

一条连接一个 `tokio::spawn` 任务，内部是读循环：

```
accept 升级
  → 等待 hello（超时 5s）
  → 校验 token + 版本
  → 回 ready
  → loop { 读一帧 → 分发 → 写回 }
```

- 连接上**不保存游戏状态**。每条 `command` 自带 `platform` / `channelId` / `userId`，
  处理逻辑完全无状态，任何一条连接都能处理任何一条消息。
- 写回时用同一条连接；`channelId` 原样带回，由 Koishi 负责路由到具体群。

## 四、命令分发

### 4.1 文本解析（v1 规则）

```
"签到"          → (指令::签到, [])
"生产 100"      → (指令::生产, ["100"])
"炮击 @某人"    → (指令::炮击, ["@某人"])
```

规则：

1. 去掉首尾空白；**剥掉结尾的句号**（兼容原版的 `签到。` 习惯，但不强制）。
2. 按空白切分，第一段是指令名，其余是参数。
3. 指令名匹配用**精确匹配**，不做前缀匹配（避免 `生产` 和 `生产次数` 打架）。
4. 不在任何地方做权限判断——权限属于 `domain`（如"非联军成员不能驻军"）。

### 4.2 路由表

一个 `match` 就够了，不要引入 trait 注册表。指令多了再拆模块。

```
指令::注册     → 账号::注册(...)
指令::签到     → 经济::签到(...)
指令::炮击     → 战争::炮击(...)
指令::不识别   → 回 error { code: "unknown_command" }
```

### 4.3 身份与绑定口令

**每条消息的第一步是解析身份**，而不是解析指令：

```
(平台, userId) --查 平台绑定--> 玩家_id
```

查不到就是"未注册"：只有 `注册` 能继续，其它指令一律回 `not_registered`，
文案提示"先发 `注册`"。**不做自动注册**——自动注册会把每个平台账号都变成玩家，
跨平台绑定就没法发起了（D23）。

`注册` 在一个事务里做完两件事：建 `玩家` + 写第一条 `平台绑定`。

跨平台绑定是个**短命状态机**，状态只活在内存里：

```rust
struct 待绑定 {
    玩家_id: i64,
    目标平台: Option<String>,   // 对方输码后才填
    目标_uid: Option<String>,
    过期时间: 时间戳,
    失败次数: u8,
}

// 口令 → 待绑定。整个 server 一份。
口令池: Mutex<HashMap<String, 待绑定>>
```

- **生成**（`绑定账户`）：6 位随机数字，5 分钟有效；同一玩家已有的待绑定先删掉
  ——同时只允许一个在飞，否则"我到底在确认哪一个"没有答案。
- **确认**（`确认绑定 <口令>`）：口令存在、没过期、失败次数 < 3；再查该平台账号是否
  已经有玩家，有就拒绝（**绑定不是合并**）；通过后把 `(平台, uid)` 记进这条口令。
- **完成**（`最终同意`）：要求发起者就是口令所属玩家、目标已填；**先把对方身份显示出来**
  （平台 / uid / 昵称），玩家确认后才落库。不显示的话，这一步等于盲签。
- **过期**：不依赖定时器（进程被杀不会漏一条永远有效的口令），每次校验时比对
  `过期时间`；生成新口令时顺手扫一遍清掉过期的。

为什么放内存：它的生命周期只有 5 分钟，丢了不产生任何数据不一致，让玩家重发即可。
换成库表要多处理过期清理和并发确认，收益是"跨实例"——v1 单实例，不需要（D23）。

## 五、事务编排

**事务边界只在这里出现。** 典型形状：

```rust
let mut 事务 = 池.begin().await?;
let 玩家 = storage::查玩家(&mut *事务, id).await?;   // 读
let 结果 = domain::签到(&玩家, 现在)?;                // 纯计算
storage::写玩家(&mut *事务, &结果.新状态).await?;     // 写
事务.commit().await?;
```

要求：

- 事务里**不 await 任何外部 IO**（HTTP、其它连接），只做数据库操作。
- 跨实体操作（战争改两个玩家 + 一张联军表）用**同一个事务**，失败整体回滚。
- 条件更新用 `WHERE 旧值 = $3` 的形式，影响行数为 0 表示并发冲突，重算而不是重试写。

## 六、文案模块

`src/文案.rs` 是**玩家可见文本的唯一出口**。规则：

- 任何 `String` 要发给玩家，都必须由这里产生。
- 排版约定：标题用 `====[标题]====`，字段前缀 `■` / `□`，数值千分位。
- 文案函数接收结构化数据，返回 `String`：

```rust
pub fn 签到结果(获得: i64, 稳定度: i64) -> String
```

## 七、错误呈现

| 错误来源 | 玩家看到 | 日志里有 |
|---|---|---|
| 玩家操作不合法（资源不足、保护期） | 具体原因 | `info!` |
| 指令不存在 | `不认识的指令` | `debug!` |
| 数据库 / 内部 panic 级错误 | `系统开小差了，稍后再试` | `error!` + 完整上下文 |

**内部错误绝不把原始信息发给玩家**——那既是泄露面，也是体验灾难。
